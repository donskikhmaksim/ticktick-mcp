## Сводный вердикт

Все пять — честные read-методы без побочных эффектов, аннотация `READONLY`
проставлена через общую константу (§2.1) везде без исключений. Гейта
согласия (§3) для них не требуется — write-инвариант не нарушается ни в одном.
Существенных дефектов не найдено. Есть 2 минорных наблюдения (см. ниже),
блокеров нет.

### 2. `list_project_groups` (server.py:6068)

## Минорные наблюдения (не блокеры)

1. **Английские тексты ошибок в catch-all `except Exception`.** Все пять
   инструментов при неожиданном исключении возвращают `f"Error ...: {str(e)}"`
   по-английски. Формально §7.4 обязывает русский только для write-методов и
   отказов (`### 7.4` начинается со слов «Весь текст... включая тексты отказов»,
   но раздел живёт под заголовком «Единый формат вывода», который сам по себе
   заявлен как относящийся к write-методам — см. вступление §7). То есть
   формального нарушения стандарта нет, но это repo-wide паттерн (не специфичный
   для группы 5 — то же самое в `create_project_group` и других write-тулах при
   catch-all ветке), и Максим этот текст всё равно увидит. Не в рамках этой
   ревизии (read-only), фиксирую как наблюдение, не правку.

2. **Нет прицельных unit-тестов** на сами эти 5 функций. В `tests/test_task_activity.py`
   и `tests/test_slice1_real_gates.py` встречается только фейковый метод
   `get_trash()` внутри mock-клиента, используемый для ДРУГИХ тестов (не тест
   поведения самого `get_trash`-тула). §13 стандарта явно требует тесты в первую
   очередь для write-методов и рефлексивного теста гейта — для read-тулов
   жёсткого требования нет, но при broad `except Exception` баг доступа к полю
   словаря (например, переименуют ключ `'score'` в API TickTick) будет тихо
   проглочен и вернётся как обтекаемая ошибка, а не упадёт в CI. Кандидат на
   лёгкий smoke-тест (мок-клиент → проверка, что нужные подстроки есть в выводе),
   не блокер.
