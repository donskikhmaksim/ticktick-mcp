# DESIGN: единый формат ответа пишущих инструментов ticktick-mcp

Проект от 2026-07-27. Только проектирование — код НЕ меняется. Относится к
задаче #29, часть «формат вывода». Базируется на аудите
`docs/PIPELINE_ticktick_mcp.md` (разделы 4 и 6).

**Что НЕ входит в эту спеку** (отдельные параллельные агенты): механизм
подтверждения (гейты, манифесты, слово-пароль) и классификация «какой
инструмент насколько опасен». Здесь только про то, КАК инструмент
РАССКАЗЫВАЕТ пользователю о том, что он сделал.

Термины простыми словами:
- **Пишущий инструмент** — тот, что реально что-то меняет в TickTick (создаёт,
  правит, удаляет, перемещает задачу/проект/тег/чек-ин). Их ~24 (см. раздел 2
  аудита). Инструменты «только чтение» (списки, поиск) этой спеки не касаются.
- **operation_report / пруф** — независимая пост-проверка: сервер сам
  перечитывает живое состояние TickTick и сверяет с тем, что записал в
  журнал. Отвечает на вопрос «а изменение реально применилось?».
- **Доставка** — дошёл ли текст инструмента до пользователя В ЧАТ. Инструмент
  всегда ВОЗВРАЩАЕТ строку, но показать её пользователю или пересказать
  своими словами решает МОДЕЛЬ (Claude). Отсюда «пусто в чате».


## 0. Проблема в одном абзаце

Сейчас два дефекта. **(A) Разнобой форматов**: основной кластер (задачи)
отвечает по-русски, с эмодзи, журналом и пруфом; а `create_project` и
`checkin_habit` — короткой английской фразой без журнала и без пруфа (аудит,
раздел 4, строки 210–213, 263–266). **(B) Дырявая доставка**: инструмент
возвращает насыщенный текст, но модель часто резюмирует его своими словами
или молчит — и пользователь видит «пусто» либо огрызок (аудит, строки
214–229). Решение: один markdown-шаблон для ВСЕХ пишущих инструментов + набор
приёмов, которые физически повышают шанс, что нужное дойдёт до чата.


## 1. Единый markdown-шаблон ответа

### 1.1. Каркас (4 блока, всегда в этом порядке)

Каждый ответ пишущего инструмента состоит максимум из четырёх блоков. Первые
два — обязательны всегда; блоки 3 и 4 — по наличию.

```markdown
### <эмодзи-статус> <ОДНА строка-заголовок: что сделано, числом и объектом>

<тело: по одному markdown-буллету на объект, объекты — НАЗВАНИЯМИ, не id>

<опционально: блок «Проверка/предупреждения», если сервер что-то заподозрил>

<пруф-блок: independent operation_report — приклеен сервером, см. раздел 3>
```

Правила каркаса:
1. **Заголовок-первым, `###`, одна строка.** Это самое важное — что именно
   произошло. Модель, даже если решит «сократить», почти наверняка сохранит
   первую строку. Поэтому заголовок должен быть самодостаточным: прочитав
   ТОЛЬКО его, пользователь понимает исход.
2. **Объекты — названиями в «ёлочках» и `**жирным**`**, никогда сырым id в
   тексте.** id живёт только внутри технической строки пруфа
   (`operation_report(record_id="…")`), не в человекочитаемой части.
3. **Числа явно.** «Создано **3**», «Удалена **1**», «Перемещено **5**» — число
   даёт пользователю моментальную сверку с тем, что он просил.
4. **Пруф-блок — последним и приклеен сервером** (не «ссылкой-предложением
   вызвать operation_report», а уже готовым текстом). Подробно — раздел 3.

### 1.2. Эмодзи-легенда (единая, замороженная)

Легенда уже де-факто сложилась в коде — фиксируем её как канон и запрещаем
вводить новые значки без обновления этой таблицы.

| Эмодзи | Значение | Когда |
|---|---|---|
| ✅ | успех, подтверждено | объект создан/изменён/удалён и это подтверждено |
| ⚠️ | предупреждение | сделано, но с оговоркой (не туда попало, не проверилось) |
| ❌ | ошибка / расхождение | не получилось, либо пруф показал несоответствие |
| 🛑 | жёсткий стоп | инструмент отказался (не совпал confirm и т.п.) — «ничего не сделано» |
| ↷ | пропущено | нечего делать / дубль / уже в нужном состоянии |
| 🧾 | пруф / журнал | заголовок independent operation_report |

Примечания:
- Сейчас в коде рядом ходят два «успеха» — `✓` (ASCII-галочка в старом тексте)
  и `✅` (эмодзи). Канон — **`✅`**; `✓` вывести из употребления.
- `✗` (отказ в `abandon`/`duplicate`) свести к `🛑` (отказ инструмента) либо
  оставить внутри тела как маркер «не буду делать» — но НЕ как статус-эмодзи
  заголовка. В заголовке только шесть значков из таблицы.

### 1.3. Статус-эмодзи заголовка — как выбирать

- Всё прошло и подтверждено → `✅`
- Сделано, но есть предупреждения в блоке проверки → `⚠️`
- Инструмент отказался что-либо делать → `🛑`
- Делать было нечего (дубль/уже так) → `↷`
- Частичный успех (часть создана, часть с ошибкой) → `⚠️` в заголовке,
  а разбивка ✅/❌ по объектам — в теле.


## 2. Проход по группам инструментов: где сейчас расходится и как свести

Опираюсь на карту инструментов из раздела 2 аудита. Три уровня текущего
качества формата:

### Группа A — «эталон» (менять почти нечего, только причесать до markdown)
`create_tasks` / `update_tasks` / `delete_tasks` / `complete_tasks` /
`move_tasks` / `execute_task_creation` / `execute_task_deletion` /
`execute_declutter` / `restore_tasks` / `abandon_task` / `duplicate_task` /
`create_subtask`.

Сейчас: русский, эмодзи, `_report_line(rid)` в конце, разбивка
создано/предупреждения/ошибки (`_create_tasks_impl`, server.py:1067–1080).
Расхождение с шаблоном: тело — плоский текст (`"Создано N:\n" + ...`), а не
markdown-заголовок `###` + буллеты. Пруф часто идёт **ссылкой** (`_report_line`
= «вызови operation_report(...)»), а не приклеенным текстом.

Как свести: (1) обернуть в каркас 1.1 — первую строку сделать `### ✅ Создано N…`;
(2) объекты — буллетами; (3) заменить `_report_line`-ссылку на серверную
склейку готового пруфа (раздел 3) везде, где есть `record_id`, а не только в
`execute_*`.

### Группа B — «скудный / англоязычный» (главные жертвы задачи #29)
`create_project` (:3743) и `checkin_habit` (:4719).

Сейчас: английская плоская фраза, без эмодзи, без журнала, без пруфа. Это и
есть «явный разнобой» из аудита (строки 210–213, 263–266). Пример «до/после» —
раздел 4.

Как свести: переписать оба под каркас 1.1 на русском. `create_project` не
пишет в journal (создание проекта не журналируется) — значит у него не будет
пруф-блока; вместо него в тело добавить **лёгкую inline-проверку** («проект
**«…»** теперь в списке — да/нет»), чтобы блок 4 не был пустым. `checkin_habit`
аналогично: показать название привычки, дату, статус, значение — русским
языком с ✅/↷.

### Группа C — «SOFT без пруф-склейки» (тихие изменения)
`set_task_parent` / `unset_task_parent` / `set_task_tags` /
`create_project_group` / `delete_project_group` / `move_project_to_group` /
`add_task_comment` / `update_task_comment` / `delete_task_comment` /
`attach_file_to_task` / `create_tag` / `rename_tag` / `delete_tag` /
`update_project` / `archive_project` / `create_project_column`.

Сейчас: часть возвращает `_report_line(rid)` (ссылку), часть — вообще плоскую
строку. Ни у кого нет приклеенного пруфа.

Как свести: единый каркас 1.1. Там где есть `record_id` в журнале — приклеивать
пруф сервером. Там где операция не журналируется (теги, группы проектов) —
как в группе B: короткая inline-проверка в теле вместо пруф-блока, чтобы
структура ответа была одинаковой у всех.

> Важно: свести форматы = свести ТОЛЬКО текст ответа. Гейты/подтверждения не
> трогаем — это другой агент. Инструмент как исполнялся, так и исполняется;
> меняется лишь то, что он печатает.


## 3. Как МАКСИМИЗИРОВАТЬ доставку до пользователя

Ключевой факт из аудита (строки 173–185): на уровне протокола MCP формат у
всех инструментов ОДИНАКОВЫЙ (все `-> str`, FastMCP оборачивает в текстовый
content-блок). Значит «пусто в чате» — это НЕ сервер отдал структуру вместо
текста, а **модель не перепечатала** возвращённый текст. Отсюда — приёмы,
которые давят на эту точку. По убыванию силы:

**Приём 1 (самый сильный) — серверная принудительная склейка пруфа.**
Это уже делает `execute_task_creation` (server.py:1301–1305): сам находит
`record_id` в своём результате регэкспом и дописывает готовый
`_build_operation_report(...)` В КОНЕЦ строки. Пруф физически становится
частью ответа инструмента — модели не нужно отдельно вызывать
`operation_report`. **Распространить этот паттерн на ВСЕ пишущие инструменты,
у которых есть journal-запись** (сейчас — только двухфазные execute_*).
Это закрывает пункт 3 из «причин пусто» аудита (строки 226–229).

**Приём 2 — короткий самодостаточный заголовок первой строкой.**
Даже когда модель «сокращает», она почти всегда сохраняет начало. Поэтому
`### ✅ <что сделано, числом и названием>` первой строкой даёт: пользователь
видит исход, даже если всё остальное модель проглотила.

**Приём 3 — явная директива модели внутри текста.**
`operation_report` уже заканчивается строкой `[агенту: перепечатай этот отчёт
пользователю ДОСЛОВНО — это серверная проверка, не заменяй её своим
пересказом]` (server.py:2266–2267), а докстринги просят «reprint VERBATIM»
(:1176, :1900, :3272). Свести к ЕДИНОЙ формулировке этой директивы и ставить
её в конце пруф-блока у всех инструментов. Формулировать коротко и по-русски,
одинаково везде (сейчас часть по-английски в докстрингах, часть по-русски в
тексте — разнобой).

**Приём 4 — директива в докстринге инструмента (протокол «спроси → сделай →
докажи»).** Слабее приёма 3 (докстринг модель видит ДО вызова, а склейку —
ПОСЛЕ), но полезно для единообразия: у каждого пишущего инструмента одна и та
же строка в докстринге «верни результат пользователю ДОСЛОВНО, не пересказывай».

### 3.1. Честный предел гарантии

**100% доставки без клиентского виджета недостижимо.** Причины:
- Финальный видимый ответ в чате генерирует МОДЕЛЬ. Сервер может положить
  текст в content-блок инструмента, но не может заставить модель дословно его
  перепечатать в свой ответ. Все приёмы 1–4 — это повышение вероятности, а не
  гейт.
- Приём 1 (склейка) даёт максимум: пруф физически внутри ответа инструмента,
  и во многих MCP-клиентах (Claude Desktop) результат инструмента показывается
  пользователю в раскрывающемся блоке САМ, помимо текста модели. Но: (а) блок
  часто свёрнут — пользователь может не раскрыть; (б) не все клиенты его
  показывают; (в) если модель ещё и напишет «готово, создал задачу» — человек
  поверит модели и не полезет в блок.
- Единственный способ приблизиться к 100% — **клиентский виджет** (UI-элемент
  на стороне хоста, который рендерит структурированный результат гарантированно
  и вне зависимости от текста модели). Это выходит за рамки MCP-сервера — нужен
  контроль над клиентом. Пока его нет, потолок такой:

| Механизм | Потолок доставки | Замечание |
|---|---|---|
| Только докстринг «reprint» | низкий | модель часто игнорирует |
| + директива в тексте ответа | средний | зависит от внимания модели |
| + серверная склейка пруфа (приём 1) | высокий | текст физически в ответе инструмента; виден в раскрытом блоке клиента даже если модель молчит |
| + клиентский виджет | ≈полный | вне зоны сервера; отдельная задача |

Вывод для Максима: приёмом 1 + заголовком-первым мы уходим от «пусто» к
«почти всегда что-то осмысленное дошло», но железную гарантию «пользователь
ТОЧНО увидел полный пруф» даёт только виджет, которого сейчас нет. Это надо
честно держать в голове и не путать «сервер сделал всё, что мог» с «доставка
гарантирована».


## 4. Примеры «до / после»

### 4.1. `create_project` (группа B)

**До** (server.py:3743, английский, без пруфа):
```
Project created successfully:

<format_project(project)>
```

**После** (каркас 1.1, русский, с inline-проверкой вместо пруфа —
создание проекта не журналируется):
```markdown
### ✅ Создан проект «Финансы 2026»

- цвет `#F18181`, вид: список
- проект **есть** в списке проектов TickTick (перечитал после создания)

_[агенту: верни этот блок пользователю дословно, не пересказывай]_
```

### 4.2. `checkin_habit` (группа B)

**До** (server.py:4719, английский, плоский):
```
Habit 'Медитация' checked in for today as 'done' (value 1.0/1.0).
```

**После**:
```markdown
### ✅ Чек-ин привычки «Медитация»

- дата: сегодня (22.07)
- статус: **выполнено**, значение 1.0 / 1.0
```

А случай дубля (сейчас — строка с `↷`, server.py:4710) причёсанный:
```markdown
### ↷ Чек-ин «Медитация» не записан

- на эту дату чек-ин **уже есть** (статус done, 1.0/1.0)
- повторная запись задвоила бы значение — ничего не изменено
```

### 4.3. `create_tasks` / `execute_task_creation` (группа A — причесать)

**До** (плоский текст, `_create_tasks_impl`, server.py:1067–1080):
```
Создано 2:
«Позвонить в банк»
«Купить билеты»

🧾 Независимая проверка: operation_report(record_id="abc-123").
```
(в `execute_task_creation` сюда уже приклеивается полный отчёт — приём 1)

**После** (тот же смысл, но каркас 1.1; пруф приклеен готовым текстом ВСЕГДА,
а не ссылкой):
```markdown
### ✅ Создано 2 задачи

- **«Позвонить в банк»** → проект «Финансы»
- **«Купить билеты»** → проект «Отпуск»

### 🧾 Независимый отчёт — `abc-123`
_22.07 15:04 · журнал операции ⇄ живое состояние TickTick_

- ✅ **«Позвонить в банк»** — создана, проект совпал
- ✅ **«Купить билеты»** — создана, проект совпал

**Итог: ✅ 2 подтверждено, ❌ 0 расхождений.**
_[агенту: перепечатай этот отчёт пользователю дословно — это серверная проверка]_
```

Разница с «до»: (1) заголовок-первым с числом; (2) объекты буллетами с
назначением; (3) пруф — готовым текстом, а не ссылкой «вызови operation_report»;
(4) единая директива-приписка.


## 5. Чек-лист приведения к единому формату (для реализации, вне этой спеки)

1. Ввести один хелпер-обёртку, собирающий каркас 1.1 (заголовок + тело +
   проверка + пруф) — чтобы все пишущие инструменты звали его, а не лепили
   строки руками. Это гарантирует единообразие структурно, а не «на глаз».
2. Обобщить приём 1 (склейка пруфа по `record_id`) из `execute_*` на все
   журналируемые пишущие инструменты.
3. Для нежурналируемых (проекты, теги, группы, чек-ин) — inline-проверка в
   теле вместо пруф-блока, единым помощником.
4. Перевести `create_project` и `checkin_habit` на русский + каркас.
5. Свести все «reprint VERBATIM» к одной русской формулировке директивы и
   ставить её в конце пруф/тело-блока у всех.
6. Заморозить эмодзи-легенду (раздел 1.2), вывести `✓`→`✅`.

Всё это — только про ТЕКСТ ответа. Гейты, манифесты и слово-пароль не
затрагиваются (отдельный агент).
