## 1. Таблица риска (§2.3)

Легенда обратимости: ✅ легко (обычная операция отменяет эффект) /
⚠️ частично (эффект снимается, но что-то безвозвратно теряется — старое
значение поля, порядок, факт исходного состояния) / ❌ необратимо (нет
операции, которая вернёт исходное состояние).

## 2. Список внешних потребителей сигнатур (§12)

**Список потребителей не задокументирован явно нигде в репозитории — задача
на будущее.** В коде есть только косвенное свидетельство существования
headless-потребителей: механизм `TICKTICK_AUTOMATION_KEY_<name>` (см.
`_load_automation_keys`, `ticktick_mcp/src/server.py`) поддерживает несколько
именованных ключей одновременно («один ключ на потребителя, чтобы можно было
отозвать один без остальных» — комментарий в коде), что подразумевает больше
одного клиента с `automation_key` в проде. Однако ни имена реальных
потребителей (боты/n8n/скрипты), ни какой набор параметров/инструментов они
реально вызывают, нигде не зафиксированы. Не выдумываю конкретных
потребителей — фиксирую факт отсутствия списка, как требует задание 16.5.

Практическое следствие: любое изменение сигнатуры write-инструмента ДОЛЖНО
по умолчанию следовать процедуре §12 (только опциональные добавления,
deprecated-алиасы вместо переименований) на случай необнаруженных
потребителей, а не полагаться на то, что «список пуст, значит менять можно
свободно».

## 3. Принятые отступления от СТАНДАРТА (код НЕ меняется)

### 3.1 RAM-манифест declutter (§16.6 → STANDARD.md `references/gate.md` §3.5)

`plan_declutter(..., persist="ram")` — **дефолт**, и он формально не
соответствует букве §3.5 («манифест должен лежать в durable-хранилище, если
сервер может рестартовать между планом и подтверждением» — Railway рестартует
при каждом деплое).

Это **осознанное решение Максима**, не баг:
- `plan_declutter(..., persist="sheet")` существует как явная альтернатива
  (durable, переживает рестарт — см. `docs/DESIGN_sheet_backed_declutter.md`)
  и НЕ убирается.
- Дефолт остаётся `"ram"`, чтобы не менять поведение существующих вызовов
  байт-в-байт (см. `docs/AUDIT_group12_memo.md` §«Главный вопрос»).
- Компенсация: TTL манифеста явный, повторный `plan_declutter` без потери
  данных TickTick (ничего не мутировано до `execute_declutter`), и при
  отсутствии RAM-манифеста `execute_declutter`/`resume_declutter` пробуют
  sheet-манифест как фолбэк (`server.py` ~4260–4269).

**Код не меняется, дефолт не переключается этим пакетом.**

### 3.2 `MIN_CONSENT_GAP=0` для тира 🟡 (§16.7 → `references/gate.md` §3.3 п.5)

`_gate_batch` (server.py ~2502–2505) использует `MIN_CONSENT_GAP=0` для
тира 🟡, тогда как тир 🔴 (`_require_consent`) держит ненулевой анти-дуплет
зазор по умолчанию.

Стандарт прямо разрешает это как частный случай: «для методов с высокой
частотой (рутинные чек-ины) МОЖЕТ быть 0, но остальные проверки — нет»
(`references/gate.md` §3.3 п.5). Это **задокументированное решение репозитория**
(`docs/DESIGN_approval_gate.md`), закрывающее конкретную дыру: сделать тир 🟡
пригодным для частых батч-операций (update/complete/move/tags), не ослабляя
ни привязку к манифесту, ни проверку утвердительности `user_reply`, ни
одноразовость — снимается ТОЛЬКО временной зазор.

**Код не меняется.**

### 3.3 Presigned-ссылки `get_attachment_download_url` (§16.8 → `references/classification.md` §2.2)

✅ **Подтверждено Максимом 2026-07-29.** `get_attachment_download_url` —
read-метод (аннотирован `READONLY`), но выдаёт bearer-capability (временную
подписанную ссылку с TTL) на скачивание вложения задачи.

Формально это пограничный случай §2.2 («read-метод не значит безвредный, если
выносит данные за пределы личного контура») — но здесь личный контур не
пересекается: ссылка даёт доступ ровно к тому же вложению, которое сам
запрашивающий уже видит через `list_task_attachments`/контекст задачи, а не к
чужим данным. Это выдача доступа к УЖЕ доступному содержимому, а не секрет
сервиса (не токен API TickTick, не `automation_key`, не `MCP_SECRET`).

**Важно отличать от находки #41 (SSRF, `security-checklist.md`):** та про то,
что СЕРВЕР сам делает исходящий `requests.get()` по чужому URL
(`attach_file_to_task`) — здесь никакого fetch нет, метод только генерирует
и возвращает ссылку; скачивать по ней будет вызывающий (человек/Claude), не
сервер. Эти два пункта НЕ связаны.

**Код не меняется** — уже реализовано корректно (TTL, `READONLY`).

### 3.4 `create_attachment_upload_url` + `PUT /ul/{token}` (§16.9)

`create_attachment_upload_url` (аннотация отсутствует — не READONLY, но и без
`_require_consent`/`_gate_single`) выдаёт одноразовую подписанную ссылку;
фактическая мутация (заливка файла) происходит ВНЕ MCP-вызова — человек или
скрипт делает `PUT` на HTTP-роут `/ul/{token}` этого же сервера.

Это **документированное исключение из инварианта §3** (архитектурно
гейт-в-процессе неприменим: к моменту PUT-запроса модели/чата в цепочке уже
нет — нечему показать план и получить «да»). Подтверждено Максимом
(`PLAN_retrofit.md` §1 п.4). Компенсирующие меры, реализованные пакетом 9
(`server.py` HTTP-роуты, ~274–358):

1. **Identity-guard** — `/ul` проверяет, что `task_id`/`project_id` из токена
   всё ещё соответствуют живому состоянию TickTick перед принятием файла.
2. **Post-verify** — после приёма файла роут перечитывает вложения задачи и
   подтверждает, что новое вложение реально появилось.
3. **Аудит-лог** — факт использования токена (кто, когда, какой task_id)
   пишется в тот же журнальный механизм, что и остальные write-операции
   (`_op_journal`), так что `operation_report` применим и здесь.
4. **Одноразовость токена и TTL** — токен `/ul` работает ограниченное время
   и предназначен для одного использования (см. `create_attachment_upload_url`
   докстринг: `ttl_minutes`).

**Код не меняется этим пакетом** — эти меры уже реализованы в пакете 9;
здесь только фиксация исключения в `docs/`.

## Известная неточность в соседнем документе (не пункт пакета 16, зафиксировано для видимости)

`docs/ALL_METHODS_MECHANICS.md` в шапке указывает источником коммит `ea3f839`
— это ДО пакетов 1–15 ретрофита. По факту текущего `server.py` часть отметок
🟢/🟡/🔴 в том файле уже не совпадает с кодом (например, `create_project`,
`update_project`, `archive_project`, `create_project_group`,
`delete_project_group`, `move_project_to_group`, `create_subtask`,
`abandon_task`, `duplicate_task`, `add_task_comment`, `update_task_comment`,
`delete_task_comment`, `create_project_column`, `attach_file_to_task` теперь
реально гейтятся через `_gate_single`/`_gate_batch`, а документ по ним всё
ещё пишет «🟢, без гейта»). Пакет 16 владеет `docs/*`, но полная построчная
ревизия полутора-тысячестрочного файла — отдельный объём работы, не входящий
в перечисленные пункты 16.1–16.12; эта таблица (`RISK_AND_DEVIATIONS.md`)
уже даёт актуальную (проверенную по докстрингам текущего кода) картину гейтов
по каждому write-методу, так что расхождение не блокирует ничего в этом
пакете — но `ALL_METHODS_MECHANICS.md` стоит перегенерировать отдельным
проходом в будущем.
