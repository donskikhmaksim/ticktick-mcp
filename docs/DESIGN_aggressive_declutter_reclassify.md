## 0. TL;DR

Текущий declutter слишком труслив: он кластеризует дубли **лексически**
(token-Jaccard ≥ 0.6) и по умолчанию делает **KEEP-BOTH**. На реальном Fix&Roll
это ловит **4 кластера / 8 задач из 209**. А у Максима дубли — **семантические**
(один заказ `26AD18286` размазан по 8 задачам разными словами; «разобраться со
страховками» ×5; лицензии CSLB ×15). Лексика их не видит.

Решение: **семантический многоролевой проход через шим**, где кластеризацию и
вердикты делает LLM (читает смысл названий+контента), а не Jaccard; агрессивность —
набор параметров; состояние и одобрение — в Sheet-манифесте (durable, resume);
исполнение — только по «да» Максима.

**Главный блокер durability:** шим на проде **есть**
(`CLAUDE_CLI_URL`+`CLAUDE_CLI_TOKEN` заданы), но Sheet-persist **не настроен**
(`DECLUTTER_SHEET_ID` / `GSHEETS_SA_JSON` в ticktick-mcp отсутствуют). Без него
план живёт в RAM (TTL 1ч, гибнет при рестарте Railway) — итеративный тюнинг на 50
прогонов на нём невозможен. Настройка Sheet = **пререквизит №1**.

## 4. Многоролевая архитектура

Философский сдвиг vs текущего кода: **кластеризацию дублей делает LLM
семантически** (не Jaccard). Jaccard остаётся только как дешёвый **пре-фильтр**,
чтобы не пихать в шим все 209×209 пар — он расширяет сеть кандидатов, а решает
**судья**. Роли — отдельные системные промпты, гоняются оркестратором батчами,
пишут строки в Sheet-манифест.

### Роли

**R0. Оркестратор** (код, не LLM). Читает открытые задачи scope, режет на батчи,
держит каждый шим-вызов < `_DC_SHIM_TIMEOUT`, а весь проход < 60с MCP-таймаута
через **поэтапную запись в Sheet + resume** (не «один гигантский вызов»). Логика:
1. тянет задачи (v2, с `columnId`, content, dueDate, priority, modifiedTime);
2. лексический пре-кластер (Jaccard ≥ `SEMANTIC_PREFILTER`, широкий) → группы-кандидаты;
3. по каждому батчу зовёт роли R1–R5 (concurrent, как сейчас judge+smart);
4. складывает вердикты в actions → строки Sheet (`plan_declutter(persist="sheet")`);
5. если не уложились в один проход — пишет прогресс, следующий вызов `resume`.

**R1. Судья дублей (агрессивный).** Вход — батч кластеров-кандидатов (название +
краткий контекст: проект, колонка, due, приоритет). Задача: для каждого кластера
решить, это **один и тот же пункт** (слить, выбрать `keep`) или разные. Отличие от
текущего `_dc_judge_fn`: **дефолт = СЛИТЬ при совпадении намерения**, keep-both
только при явно разном объекте/скоупе. Явно ищет «одно дело разными словами» и
«оплатить/одобрить/отследить один и тот же инвойс». Черновик промпта — §7.

**R2. Smart-переформулировщик.** Вход — расплывчатые/короткие названия. Выход —
`глагол + что именно + (зачем/для чего)`, тем же языком, по методичке разбора Inbox.
Строже текущего `_dc_smart_fn`: не «мягко предложить», а **давать конкретную
формулировку** для всего, что не самодостаточно из названия. «Списание расходов» →
«Занести списание расходов F&R за <период> в бухгалтерию». Черновик — §7.

**R3. Критик нужности («нужна ли задача вообще»).** НОВАЯ роль. Вход — названия
(+контекст). Выход по каждой: `verdict ∈ {keep, junk, obsolete, unclear}` + reason.
`junk` = очевидный мусор/не на месте (#106 муз-ссылка, #183 «HIS»), заведомо
неактуальное, или «placeholder-задача» («Основная задача по лидогенерации»).
Отличие от текущего obsolete-эвристика (только по датам, flag-only): критик судит
**по смыслу названия** — Максим прав, что «часто по названию видно, что шлак».
`junk`/`obsolete` → строка `flag_junk`/`flag_obsolete` (см. §6, risk-split:
удаление всегда через аппрув).

**R4. Классификатор колонок.** НОВАЯ роль. Вход — задача + список целевых колонок
(таксономия §5). Выход — `target_column` + confidence + reason. Обратимо (move
между колонками) → можно агрессивно, decision=approved по дефолту.

**R5. Umbrella-группировщик.** Уже есть эвристикой (`_dc_group_candidates`,
word-prefix). Оставить как есть + опционально дать шиму подтверждать неочевидные
umbrella (CSLB-пакет, страховки-пакет — они уже частично оформлены родителем #175
«CSLB … план» и #128 «страховки — 3 позиции»).

### Как компонуются (один проход)

```
tasks ──► [R0 префильтр] ──► кандидаты-кластеры
                     │
      concurrent ────┼──► R1 судья дублей   ──► delete-rows (keep→id)
                     ├──► R2 smart-rewrite   ──► rename-rows
                     ├──► R3 критик нужности ──► flag_junk / flag_obsolete rows
                     ├──► R4 классификатор   ──► reclass-rows (column move)
                     └──► R5 umbrella        ──► group-rows
                                    │
                            _dc_analyze-подобная сборка → actions
                                    │
                     plan_declutter(persist="sheet") → строки в Declutter Log
                                    │
                    Максим правит decision в таблице → execute по «да»
```

Приоритет разрешения конфликтов (какая роль «съедает» задачу): **delete > group >
reclass > rename > flag**. Задача, помеченная на удаление, не переименовывается и
не реклассифицируется (как сейчас через `consumed`-множество в `_dc_analyze`).

### Удержание под 60с-таймаутом

- Роли гоняются **concurrent** (`asyncio.gather`/`to_thread`) — как сейчас
  judge+smart. Wall-clock ≈ max(ролей), не сумма.
- Каждый шим-вызов ограничен `_DC_SHIM_TIMEOUT` (25с).
- **Батчинг:** не весь список в один промпт. Оркестратор шлёт кластеры/кандидаты
  чанками (напр. ≤ 40 задач/промпт). Много мелких быстрых вызовов > один медленный.
- **Поэтапно через Sheet:** каждый готовый батч → `append_rows` сразу. Если проход
  упёрся в таймаут/лимит — `resume_declutter` продолжает с непройденных задач
  (состояние в таблице, не в контексте LLM). Это и есть «≤50 прогонов тюнинга»:
  крутим качество плана, а не сносим.

## 6. Ручки агрессивности + risk-split

Все — параметры (env/аргумент `plan_declutter`), дефолты сдвинуты «жёстче
реальности, но не на явную ерунду»:

| Ручка | Сейчас | Предлагаемый дефолт (агрессивный) | Эффект |
|---|---|---|---|
| `SEMANTIC_PREFILTER` (Jaccard для сети кандидатов) | `_DC_FUZZY_THRESHOLD=0.6` | **0.30** | шире невод; решает судья, не порог |
| Кластеризация | лексическая | **семантическая (R1 по смыслу+контенту)** | ловит `26AD18286`×8 и т.п. |
| keep-both bias | ON (сливаем только если судья явно уверен) | **OFF** (сливаем при совпадении намерения; keep-both только при явно разном объекте) | меньше «оставить обе» |
| 3+-member fuzzy auto-delete | запрещён (→ flag) | **разрешён, если R1 уверен и выбрал keep** | схлопывает большие нести |
| Критик нужности (R3) | нет (obsolete только по датам) | **ON, судит по смыслу названия** | «шляпа по названию» → flag_junk |
| obsolete | flag-only | **flag + предложение delete (аппрув)** | протухшее реально уходит (по «да») |
| Reclass (R4) | нет | **ON, decision=approved** (обратимо) | раскладка по §5 |

**Разделение риска (жёсткость ∝ обратимости):**

- **Обратимо → агрессивно, decision=approved по дефолту:** `rename`, `reclass`
  (move колонки), `group`, все `flag_*`. Ошибся — вернул одним движением.
- **Точные дубли (identical normalised title) → авто-безопасны:** сливаются без
  шима (как сейчас `exact=True`), decision=approved.
- **`delete` (семантические дубли + junk + obsolete) → смелее, но ВСЕГДА через
  аппрув:** строка пишется `decision=approved` (чтобы Максим видел предложение
  сразу активным и «10→9 ок, 1 хрень» правил быстро), но **исполнение — только
  после `execute_declutter(confirm="DECLUTTER N")`**. Инвариант `keep_id ∉ deletes`
  (§5.9 sheet-design) защищает от само-противоречий.

Максим — финальный аппрувер: правит колонку `decision` в таблице (approved→rejected)
или говорит в чат. Никакого авто-сноса (§8).

## 7. Черновики промптов ролей

Все — `system` + `prompt`, ответ строго JSON, через `_dc_shim_json` (как есть).

### R1. Судья дублей (агрессивный)
```
system: Ты вычищаешь дубли в списке задач владельца. Отвечай только JSON.
prompt:
Ниже кластеры ПОХОЖИХ задач (название + проект/колонка/срок/приоритет). Для
КАЖДОГО реши: это ОДНО И ТО ЖЕ дело (можно слить), или разные?
ПРАВИЛО (агрессивное): если задачи ведут к одному результату/объекту — это
дубли, СЛИВАЙ, даже если слова разные («оплатить инвойс X» = «одобрить инвойс X»
= «отследить оплату X», если X один). KEEP-BOTH только когда объект/скоуп ЯВНО
разный. Для дублей выбери keep = индекс версии с макс. деталями (срок, сумма,
приоритет, контекст).
<кластеры>
Ответ СТРОГО JSON: [{"i":0,"is_duplicate":true,"keep":1,
  "delete_idx":[0,2],"reason":"<кратко: почему одно дело>"}]
```

### R2. Smart-переформулировщик
```
system: Ты переформулируешь задачи в конкретный вид. Отвечай только JSON.
prompt:
Ниже расплывчатые/короткие названия. Для каждого дай формулировку вида
«ГЛАГОЛ + ЧТО именно + (зачем/для чего)», тем же языком. Убери «разобраться
с…», «задача по…», «вопрос …» — замени на конкретное действие. Если из названия
непонятен объект — выведи его из контекста (проект Fix&Roll: гаражные ворота, LA).
Срок добавлять НЕ обязательно. Если название уже конкретное — new_title="".
<нумерованные названия+контекст>
Ответ СТРОГО JSON: [{"i":0,"new_title":"<или пусто>","reason":"<кратко>"}]
```

### R3. Критик нужности
```
system: Ты решаешь, нужна ли задача вообще. Отвечай только JSON.
prompt:
Ниже задачи (название + контекст). Для КАЖДОЙ реши:
- "keep"     — осмысленная рабочая задача.
- "junk"     — мусор/не на месте/placeholder (ссылка не туда, одно непонятное
               слово, «основная задача по…» без сути).
- "obsolete" — по смыслу уже неактуальна/сделана/потеряла смысл.
- "unclear"  — не хватает данных, оставить и уточнить.
Будь решителен: по названию часто видно, что это шлак. Но не трогай
конкретные рабочие задачи с суммами/сроками/контрагентами.
<задачи>
Ответ СТРОГО JSON: [{"i":0,"verdict":"junk","reason":"<кратко>"}]
```

### R4. Классификатор колонок
```
system: Ты раскладываешь задачи по колонкам канбана. Отвечай только JSON.
prompt:
Колонки: 💰 Финансы и налоги | 🪪 Лицензии·бонды·страховки | 📣 Маркетинг и
продажи | 🚚 Закупки и оснащение | 🛠 IT и системы | 🚀 Запуск и операции |
📥 TG Inbox (только если совсем неясно).
Для каждой задачи выбери ОДНУ колонку по смыслу.
<задачи>
Ответ СТРОГО JSON: [{"i":0,"column":"💰 Финансы и налоги","conf":0.9,
  "reason":"<кратко>"}]
```

## 8. Привязка к Sheet-манифесту (какие action-типы)

Опирается на схему `Declutter Log` из `DESIGN_sheet_backed_declutter.md` §3.
Расширяем множество `action` (колонка I) и `_DC_MUTATING_ROW_ACTIONS`:

| action | mutation | proposed_value (J) | decision по дефолту | исполнитель |
|---|---|---|---|---|
| `delete` | да | `keep→<id>` | approved (но apply только по confirm) | `execute_task_deletion` |
| `rename` | да | new_title | approved | `update_tasks` |
| `group` | да | `parent→<id>` | approved | `set_task_parent` |
| **`reclass`** (НОВЫЙ) | да | `column→<columnId>` | approved | `update_tasks` (columnId) / `move_tasks` |
| `flag_obsolete` | нет | — | pending | — (инфо; человек может поднять до delete) |
| **`flag_junk`** (НОВЫЙ) | нет | — | pending | — (инфо; кандидат в delete по «да») |
| `flag_dupe` | нет | — | pending | — |
| `flag_nonsmart` | нет | — | pending | — |

- `reclass` — новый мутирующий тип. Нужны: (1) `_dc_actions_to_rows` — ветка reclass
  (`column→<columnId>` + `cluster_id` пусто); (2) `_dc_rows_to_exec` — сборка
  входа для `update_tasks(columnId=…)`/`move_tasks`; (3) `_execute_declutter_from_sheet`
  — диспетч reclass в под-инструмент (identity-guard уже есть). Обратимо → низкий риск.
- `flag_junk` — как `flag_obsolete`: строка ради видимости, apply не трогает; Максим
  в таблице меняет `action` на `delete` (осознанный шаг) для тех, что реально снести.
- Колонка `column` (G) в Sheet заполняется РЕАЛЬНОЙ текущей колонкой (из `columnId`
  через get_task_info/v2), чтобы reclass-строка показывала «из X → в Y».
- Всё остальное (row_id, manifest_id, decision/status раздельно, snapshot_json,
  resume, идемпотентность, confirm-гонка) — **как в sheet-design без изменений**.

## 9. Пошаговый план для Sonnet

Пререквизит (§3): поднять `declutter_sheet.py` + env `DECLUTTER_SHEET_ID`,
`GSHEETS_SA_JSON` (по `DESIGN_sheet_backed_declutter.md` §8.1–8.2). Без durable-Sheet
итеративный тюнинг невозможен.

1. **Семантическая кластеризация.** Ослабить `_DC_FUZZY_THRESHOLD` до
   `SEMANTIC_PREFILTER=0.30` (env-параметр), но переосмыслить: Jaccard теперь
   только пре-фильтр → кандидаты. Ввести `_dc_semantic_cluster(candidates)` —
   батч-вызов R1, который возвращает cluster-assignment по смыслу (не только
   is_duplicate по готовым лексическим группам). Юнит-тест с моком шима.
2. **R1 судья (агрессивный).** Переписать `_dc_judge_fn` промпт (§7), убрать
   keep-both-bias-дефолт в `_dc_analyze` (шаг 1): при `is_duplicate` → merge;
   разрешить 3+-member auto-delete когда судья дал `delete_idx`+`keep`. Параметр
   `keep_both_bias: bool=False`.
3. **R2 smart.** Ужесточить `_dc_smart_fn` промпт (§7). Порог «что считать
   nonsmart-кандидатом» (`_dc_is_nonsmart_candidate`) расширить: не только ≤2
   слова, но и по стоп-паттернам («разобраться с», «задача по», «вопрос»).
4. **R3 критик нужности (новый).** `_dc_critic_fn(titles+ctx)` → verdicts;
   в `_dc_analyze` добавить ветку: `junk`→`flag_junk`, `obsolete`→`flag_obsolete`
   (+ опц. предложение delete под флагом `obsolete_propose_delete`). Concurrent с
   R1/R2 в `asyncio.gather`.
5. **R4 классификатор (новый).** `_dc_classify_fn(tasks, columns)` → target column;
   в `_dc_analyze` — ветка `reclass` (только если target ≠ current column). Список
   целевых колонок — из §5, вынести в конфиг.
6. **action `reclass` + `flag_junk`** в `_dc_actions_to_rows` / `_dc_rows_to_exec` /
   `_execute_declutter_from_sheet` / `_DC_MUTATING_ROW_ACTIONS` (§8). Заполнять
   колонку `column` реальной текущей колонкой.
7. **Оркестратор-батчинг + resume.** Убедиться, что большой scope (Fix&Roll ~209)
   режется на чанки ≤40, каждый чанк → `append_rows` сразу, а не «весь план в
   RAM/один промпт». Опереть на существующий `resume_declutter`.
8. **Параметры агрессивности** — все через аргументы `plan_declutter` / env
   (§6 таблица), дефолты = агрессивные, но каждый переключаем.
9. **Тюнинг-цикл (до ~50):** гонять `plan_declutter(scope="Fix&Roll", persist="sheet")`
   на живом проекте, смотреть план в таблице, крутить пороги/промпты — это про
   **качество плана**, НЕ авто-снос.
10. **Тесты (обяз.):** мок-шим для R1–R4; round-trip actions→rows→exec для reclass;
    keep_both_bias=False сливает то, что True оставлял; критик junk→flag_junk не
    мутирует; классификатор target==current → нет reclass-строки; обратная
    совместимость `persist="ram"` + старые declutter-тесты зелёные.

**Execute — только по человеку (§E задания, жёстко):** система генерит ПЛАН в
Sheet. Удаление/изменения — исключительно после `execute_declutter`/
`resume_declutter` с `confirm="DECLUTTER N"` от Максима. Никакого авто-исполнения.
