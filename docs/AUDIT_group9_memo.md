# AUDIT group9 — update_tasks / complete_tasks / move_tasks vs STANDARD.md

Read-only ревизия по чек-листу §16 STANDARD.md (`~/.claude/skills/mcp-development-standard/STANDARD.md`),
разделы §3/§4/§5/§6/§7. Объект: `_gate_batch` (server.py:2481) и три инструмента,
которые его используют — `update_tasks` (1601), `complete_tasks` (1935),
`move_tasks` (5334). Код НЕ менялся.

## Вердикт по разделам

**§3 Гейт plan→execute — СООТВЕТСТВУЕТ.**
`_gate_batch` — ровно одна функция, два режима (без `manifest_id` / с ним),
одно имя инструмента на оба вызова (2481–2533). `object_hash`-привязка
(§3.3 п.2) реально есть: считается при плане (2518, `_manifest_object_hash`)
и сверяется в `_require_consent` по `object_ids` при исполнении (2504–2505,
2375–2381). Явное отрицание сжигает манифест (§3.3 п.3): `_require_consent`
ставит `manifest["consumed"]=True` при негативном ответе (2383–2388) — это
именно **жёсткий отказ**, а не «попробуй ещё раз». Единственный нюанс:
`_gate_batch` жёстко передаёт `min_gap=0` для всех трёх tier-🟡 инструментов
(2502–2505) — анти-дуплет-эвристика §3.3 п.5 для них выключена полностью, не
только для «рутинных частых» операций, как в примере стандарта. Это
задокументированное архитектурное решение (docs/DESIGN_approval_gate.md,
разделение 🟡/🔴), не тихая дыра, но по букве §3.3 п.5 — расширенное
исключение, стоит зафиксировать явно как принятый компромисс.

**§4 Identity-guard — СООТВЕТСТВУЕТ.**
`_guard_task`/`_split_tasks_by_state` (618, 659) перечитывают **свежее**
состояние (`fresh=True`) для каждого элемента батча, сверяют id+title, и
container (project), когда он передан вызовом — что соответствует формулировке
стандарта «минимум три признака **из переданных вызовом**». Несовпадение →
`mismatch`, элемент не трогается, батч обрабатывает остальные независимо (это
per-item, как требует §4). Слепая мутация по одному id без title блокируется
(`_unarmed_note` явно помечает, если title не был передан — не блокирует
жёстко, но честно предупреждает пользователя postfactum вместо тихой лжи).

**§5 Post-verify — ЧАСТИЧНО СООТВЕТСТВУЕТ, есть пробел.**
Отдельный свежий запрос после мутации есть у всех трёх (`_open_by_id(fresh=True)`
после API-вызова, не переиспользование тела ответа мутации) — `update_tasks`
через `_verify_item` (1798–1813, 1880–1905), `complete_tasks`/`move_tasks`
через проверку присутствия/поля в свежем pool (2066–2076, 5413–5421). Три
исхода (успех/не удалось перепроверить/расхождение) представлены по смыслу.
**Пробел**: pre-snapshot (§5.2) отсутствует у всех трёх. `_snapshot_of()`
вызывается только в `delete_tasks` (2193) и declutter (3376) — НЕ в
`_update_tasks_impl`/`_complete_tasks_impl`/`_move_tasks_impl`. Для
`update_tasks` это прямое нарушение: §5.2 явно называет «перезапись поля»
(rewrite of a field) как случай, требующий pre-snapshot, а `update_tasks`
именно это и делает (title/content/priority/dates/tags). Без снимка
предыдущего состояния ручной откат ошибочного `update_tasks` невозможен.

**§6 Fail-closed — СООТВЕТСТВУЕТ.**
Недоступность live-состояния → отказ (`_STATE_UNAVAILABLE_MSG`), mismatch →
отказ по элементу, неаффирмативный/двусмысленный `user_reply` → отказ с
объяснением. Исключений «сделать как получится» не найдено в этих трёх
инструментах.

**§7 Единый формат вывода — НЕ СООТВЕТСТВУЕТ.**
Все три инструмента (через `_update_tasks_impl`/`_complete_tasks_impl`/
`_move_tasks_impl`) возвращают плоский текст без `###`-заголовка (§7.1 п.1) —
сравни с `create_project`/`checkin_habit`/`plan_task_deletion`, которые уже
обёрнуты в каркас `### <эмодзи> <строка>`. Легенда эмодзи (§7.2) нарушена
явно: `update_tasks`/`complete_tasks` используют ASCII `✓`/`✗` (1716, 1752,
2009, 2061, 2076) — а стандарт прямым текстом запрещает именно это: «ASCII-
варианты (✓, ✗) НИКОГДА не используются как статус» (§7.2, последняя строка).
`update_tasks` дополнительно использует `✏️`, `move_tasks` — `↪` — оба не из
замороженной легенды (✅⚠️❌🛑↷🧾). Общего хелпера-обёртки на формат (§7.1 п.5)
нет — три реализации собирают строку руками по-разному. Есть утечка
английского в fail-текстах: `complete_tasks` (2088) и `move_tasks` (5451)
падают в `except` с `f"Error completing/moving tasks: {e}"` — прямое
нарушение §7.4 («весь текст, видимый Максиму — по-русски, без исключений»).

Важный контекст: это не новая находка — `docs/DESIGN_output_format.md`
(2026-07-27, задача #29) уже классифицировал ровно эти инструменты как
«Группа A» и прописал план сведения к единому каркасу, но сам документ явно
помечен «Только проектирование — код НЕ меняется». Т.е. работа над §7 для
этих трёх инструментов **спланирована, но не реализована** — вчерашний
коммит по гейту (`_gate_batch`) её не затрагивал, и не должен был по скоупу.

## Итог

- Гейт (§3), identity-guard (§4), fail-closed (§6): вчерашняя реализация
  `_gate_batch` соответствует стандарту, включая object_hash-привязку и
  сожжение манифеста при отказе.
- Post-verify (§5): соответствует по механике «свежий запрос + сверка полей»,
  но у `update_tasks` отсутствует обязательный pre-snapshot перед перезаписью
  полей (§5.2) — единственный найденный дефект вне §7.
- Формат вывода (§7): не соответствует — старый текст, включая явно
  запрещённые стандартом ASCII-статусы `✓`/`✗`, отсутствие `###`-заголовка,
  отсутствие общего хелпера и утечку английского в двух exception-путях. Уже
  описано и спланировано в `docs/DESIGN_output_format.md`, но не внедрено.
