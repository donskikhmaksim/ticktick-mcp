# Аудит группы 2 (read-методы): приоритет/дедлайны

Дата: 2026-07-29. Read-only ревизия по чек-листу §16 STANDARD.md (гейт/identity-guard/
post-verify не применялись — методы read-only).

Методы: `get_tasks_by_priority`, `get_tasks_due_today`, `get_overdue_tasks`,
`get_tasks_due_tomorrow`, `get_tasks_due_in_days` — все в `ticktick_mcp/src/server.py`,
строки 4907–5008. Общие хелперы: `_task_due_local_date`, `_is_task_due_today`,
`_is_task_overdue`, `_is_task_due_in_days` (4734–4777), диспетчер вывода
`_get_project_tasks_by_filter` (4802–4864).

## Вердикт по методу

| Метод | Строка | Вердикт |
|---|---|---|
| `get_tasks_by_priority` | 4907 | ⚠️ работает верно, но общие дефекты ниже |
| `get_tasks_due_today` | 4933 | ⚠️ то же |
| `get_overdue_tasks` | 4950 | ⚠️ то же |
| `get_tasks_due_tomorrow` | 4967 | ⚠️ то же |
| `get_tasks_due_in_days` | 4984 | ⚠️ то же (плюс валидация `days<0` — ок) |

Логика самих фильтров-дат корректна и **консистентна** между собой:
`_task_due_local_date` — единая точка правды для all-day (zone-independent,
`dueDate[:10]` verbatim, без `.astimezone()`) и timed (`.astimezone(_USER_TZ)`)
дедлайнов; `_is_task_overdue` отдельно, но с той же развилкой all-day/timed —
никакого рассинхрона между методами не нашёл. `_USER_TZ` берёт `USER_TIMEZONE`
из окружения; в проде (`railway variables`) реально стоит
`America/Los_Angeles` — соответствует глобальному правилу Максима. Локально/по
умолчанию — `UTC` (см. `.env.template:38`), это осознанный fallback, не баг.

## Что чинить (общие для всех пяти)

1. **Блокирующий вызов вне `_run_blocking`.** Все пять — `async def`, но
   вызывают `_get_project_tasks_by_filter` синхронно, а та внутри дёргает
   `ticktick_v2.get_state()` (blocking HTTP) прямо в event loop — без
   `asyncio.to_thread`, в отличие от `get_all_tasks` (4883), который тот же
   v2-пул оборачивает в `await _run_blocking(...)`. Несогласованность с
   остальным кодом и потенциальная задержка `/health`/других сессий под
   нагрузкой (см. докстринг `_run_blocking`, 875–879, который сам это и
   объясняет). Чинить: обернуть тело `_get_project_tasks_by_filter` (или его
   вызовы) в `_run_blocking`.

2. **Нет капа на fallback-пути (без v2).** Путь через v2 капается —
   `format_task_tree(matched)` дефолтом `limit=200` с хвостом «... and N
   more.» (§10.1 соблюдён). Но official-API fallback (4831–4864, когда v2
   недоступен) собирает строку по ВСЕМ проектам и ВСЕМ подходящим задачам без
   какого-либо предела — потенциально неограниченный ответ. Нарушение §10.1.
   Чинить: применить тот же лимит (или явный cap на число задач/проектов) и в
   fallback-ветке.

3. **Язык вывода — английский, не по-русски.** Все пять читают/пишут только
   английские строки-ответы («Tasks that are 'X' (N):», «No tasks found that
   are 'X'.», «Error retrieving...», докстринги — тоже en). §7.4 требует
   русский для всего текста, видимого Максиму, «без исключений» — а write-
   инструменты в этом же файле (напр. `complete_tasks`, 1935–1968) уже это
   соблюдают и используют общий формат-хелпер с ✅/⚠️/🛑 и заголовком `###`.
   Формально §7.1 ограничивает каркас write-методами, но §7.4 (язык) сформулирован
   шире и данная группа явно выпадает из общего стиля репозитория — задел на
   будущее выравнивание, не блокер прямо сейчас.

4. **Докстрингное «Ignores closed projects» — не проверено для v2-ветки.**
   Утверждение верно и явно реализовано в fallback-пути (`if
   project.get('closed'): continue`, 4841). В v2-пути (`ticktick_v2.get_state()`
   → `syncTaskBean.update`, `ticktick_v2_client.py:235-237`) фильтрации по
   `project.closed` в коде НЕТ — предполагается, что batch/check/0 сам не
   отдаёт задачи архивных списков. Правдоподобно, но не верифицировано живым
   вызовом (вне бюджета read-only ревизии). Если предположение неверно —
   докстринг «Ignores closed projects» станет ложным для v2-режима, который
   сейчас основной путь.

## Не проблема (проверил и отклонил)

- Рассинхрон таймзон между методами — не нашёл; все пять и их хелперы читают
  дату дедлайна через единственную функцию `_task_due_local_date`.
- Капы/пагинация по TickTick API — не применимо, это не постраничные запросы,
  а фильтрация уже полученного пула задач.
