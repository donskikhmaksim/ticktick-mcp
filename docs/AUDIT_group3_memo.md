`get_recurring_tasks`, `get_engaged_tasks`, `get_next_tasks`. Гейт/identity-guard/

### 1. `get_tasks_due_this_week` (server.py:5010-5031)

- §2.2: ✅ без секретов, свой контур (личные задачи Максима).
- §10.1 капы: ✅ идёт через `_get_project_tasks_by_filter` → `format_task_tree`
  с дефолтным лимитом 200 и честным «...and N more» при усечении (server.py:4827,
  818-858).
- §10.2 таймауты: ✅ `REQUEST_TIMEOUT` на все исходящие HTTP-вызовы
  (ticktick_v2_client.py:144/168).
- Докстринг: ⚠️ утверждает «Ignores closed projects», но это верно только для
  fallback-ветки (`project.get('closed')` фильтруется, server.py:4841). Основная

  НЕ фильтрует задачи закрытых проектов вообще — `get_open_tasks`/`get_state` в

- **Вердикт: ⚠️ докстринг потенциально врёт про «Ignores closed projects» в

## Итог по группе 3

- 3 из 5 методов (`get_recurring_tasks`, `get_engaged_tasks`, `get_next_tasks`) —
  ✅ полностью соответствуют §16 для read-методов.
- 2 из 5 (`get_tasks_due_this_week`, `search_tasks`) — ⚠️ докстринг заявляет
  «Ignores closed projects», но это гарантированно верно только в
  fallback-ветке без v2; в основной (предпочитаемой) v2-ветке в коде сервера
  нет фильтра закрытых проектов — фактическое поведение зависит от того, что
  сам TickTick кладёт (или не кладёт) в `/batch/check/0` для закрытых проектов,
  что не проверялось вживую. Это нарушение принципа «докстринг не должен
  обещать поведение, которого код не гарантирует» (§16 п.9), а не подтверждённый
  функциональный баг.
- Капы (§10.1) и таймауты (§10.2) — без замечаний по всей группе.
- **Что чинить (не сделано, только рекомендация):** либо (а) реализовать
  фильтр закрытых проектов и в v2-ветке `_get_project_tasks_by_filter` /
  `search_tasks` явно (например, через `_v2_project_names()`/список закрытых
  id из `state`), либо (б) смягчить докстринг до «Ignores closed projects
  (fallback path only) / в основном режиме зависит от TickTick API» — чтобы не
  расходиться с реальной гарантией кода.
