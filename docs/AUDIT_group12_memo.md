# Аудит группы 12 — plan_declutter / execute_declutter / resume_declutter / set_declutter_decision

Дата: 2026-07-29. Прогон STANDARD.md §3/§4/§5/§6/§7/§16 по `ticktick_mcp/src/server.py`
(строки ~3981–4439). READ-ONLY, код не менялся.

## Вердикты по разделам

**§3 (гейт plan→execute).** ✅ Соответствует. Все 4 write-точки (`execute_declutter`,
`resume_declutter`, `set_declutter_decision` при `decision="approved"`) идут через
единый `_require_consent()` (server.py:2345) — ровно один гейт на весь сервер, без
пароля-эха, `manifest_id` не считается подтверждением, есть проверка отрицания
(инвалидирует манифест), словарь утверждения/отрицания серверный, анти-дуплет
`MIN_CONSENT_GAP` применяется. `decision="rejected"` в `set_declutter_decision`
корректно НЕ гейтится (безопасно, только блокирует).

**§4 (identity-guard).** ✅ Соответствует, но косвенно. Сам `execute_declutter` не
делает identity-guard напрямую — он строит суб-манифесты и делегирует в уже
аудированные `_execute_task_deletion_impl` / `_update_tasks_impl` /
`_set_task_parent_impl`, которые сверяют id+title+project по свежей перечитке
(видел на примере `_execute_task_deletion_impl`, server.py:2699 — полная триада
id/title/project с fail-closed на любое расхождение). Годная архитектура —
"не изобретать второй guard", но означает, что аудит declutter-тулов **зависит**
от корректности этих трёх shared-impl (не проверялись здесь построчно).

**§5 (post-verify).** ✅ Соответствует. Каждая под-операция (delete/rename/group)
делает отдельный свежий `_open_by_id(fresh=True)`/аналог после мутации, три исхода
✅/⚠️/❌, пруф приклеивается сервером (`_build_operation_report`), не предлагается
"вызови отдельно".

**§6 (fail-closed).** ✅ Соответствует. Отказы по протухшему/чужому манифесту, по
несовпадению `object_hash`, по неутвердительному `user_reply`, по недоступности
sheet — везде явный 🛑 текстом, ничего не "делается как получится".

**§7 (единый формат вывода).** ⚠️ Частичное несоответствие. `plan_declutter` строго
следует шаблону (`### 🧹 План...` первой строкой, самодостаточный заголовок,
эмодзи-легенда). Но `execute_declutter` **не** формирует единый `### <эмодзи>
заголовок с числом` для всего результата — просто конкатенирует суб-блоки
(`## 🗑 Удаление дубликатов`, `## ✏️ Переименования`, `## 🔗 Группировка...`),
каждый из которых сам начинается не с `###`, а с обычной текстовой строки внутри
(`_execute_task_deletion_impl` возвращает `🗑 Удалено N/M: ...` без `###`-заголовка
вообще, server.py:2789). Итог: при частичном успехе (одни строки ✅, другие ❌) нет
единого верхнеуровневого статуса, который §7.3 требует выставлять в ⚠️/❌ для всего
ответа — человек должен сам собрать общий вывод из трёх под-отчётов. Это не блокер
(данные корректны), но формально расходится с §7.1 п.1/5 (единый хелпер-обёртка,
самодостаточный заголовок). Затрагивает не только declutter — это общий паттерн
переиспользуемых suffix-impl.

**§16 чек-лист ревизии — точечно:** п.2 (один `require_consent`, все write через
него) — да, подтверждено чтением всех 4 вызовов. П.8 (единый формат) — частично не
выполнен, см. §7 выше. Остальные пункты (аннотации, докстринги, капы, аудит-лог,
тесты) не проверялись глубоко в этом прогоне — вне заданного фокуса.

## Главный вопрос: RAM-манифест durable ли по стандарту (§3.5)?

**Нет, RAM-режим (default `persist="ram"`) формально НЕ соответствует букве §3.5**,
и это осознанное, задокументированное отступление, а не недосмотр:

- §3.5 гласит: если сервер может рестартовать между планом и подтверждением
  («типично для Railway при деплое») — манифест **ДОЛЖЕН** быть durable.
  ticktick-mcp хостится на Railway → условие срабатывает буквально.
- Реализация (`docs/DESIGN_sheet_backed_declutter.md`, коммит `a643ef4`, автор —
  сам Максим) добавила durable-режим `persist="sheet"` (Google Sheet как источник
  истины, resume после рестарта, colonка `decision` правится вручную), но **опт-ин**:
  дефолт остался `persist="ram"`, явно "поведение байт-в-байт как было".
- Формулировка в коде и коммите подчёркивает выбор осознанно: "Строго opt-in:
  persist='ram' (дефолт) — поведение байт-в-байт как было". Т.е. Максим сознательно
  принял риск «план протух при деплое между `plan_declutter` и `execute_declutter`»
  для дефолтного пути, взамен получив нулевой Google-креды-overhead по умолчанию.
- Смягчающее обстоятельство: TTL манифеста 1 час, `execute_declutter` при
  отсутствии RAM-манифеста **пробует sheet как фолбэк** (server.py:4260–4269) —
  если план когда-либо писался с `persist="sheet"`, restart не фатален. Но для
  **дефолтного** RAM-плана рестарт между plan и execute = манифест теряется
  безвозвратно, ответ "план не найден/истёк" — ровно тот UX-риск, который §3.5
  предупреждает («появится соблазн ослабить гейт»).

**Вывод:** технически расхождение со стандартом есть (§3.5 — «ДОЛЖЕН», не
«может»), но это не забытый случай, а компромисс, задокументированный в
design-документе и принятый в коммите Максима. Стандарт писался позже (v1.0,
2026-07-28) чем это решение (2026-07-26) — возможно, стандарт в §3.5 фиксировал
именно этот случай как норму на будущее, а не ретроактивно требует переделать
declutter. Рекомендация: либо (а) явно занести это расхождение как принятое
исключение в `docs/` declutter-фичи со ссылкой на §3.5, либо (б) сменить дефолт на
`persist="sheet"` если частота деплоев между plan/execute на практике создаёт
проблемы — решение за Максимом, не самостоятельная правка.
