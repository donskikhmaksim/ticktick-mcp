## 1. Как прогонять тесты локально

```bash
uv venv --python 3.12
uv pip install -e .[dev]
TICKTICK_TEST_PG_DSN="postgresql://<user>@localhost/ticktick_test?sslmode=disable" \
  pytest tests/ -q
```

`TICKTICK_TEST_PG_DSN` не обязателен — без него тесты сами ищут локальный
Postgres по unix-сокету (`/tmp`, `/var/run/postgresql`) с базой
`ticktick_mcp_test` (см. §3); если и это не отвечает, тесты, которым нужна
настоящая база, пропускаются с внятной причиной, а не падают.

## 2. Структура тестов

108+ файлов в `tests/`, без `unittest`-классов — только `pytest`-функции и
фикстуры. Общие правила по всему набору:

- **Даты — только `datetime.now(tz) + timedelta`**, никогда календарные
  литералы (`datetime(2026, 8, 9)`) — иначе тест начинает падать сам по себе
  через календарный год/месяц.
- **Испортить код и убедиться, что тест краснеет** — обязательный шаг при
  написании новой проверки; зелёный тест на заведомо сломанном коде
  переписывается, а не остаётся как есть.
- Тестовые заглушки (моки TickTick API) обязаны повторять поведение настоящих
  функций один в один, включая их баги и подводные камни — на этом стоит
  отдельная структурная проверка (§12).

## 3. Настоящий Postgres для тестов долговечных планов

Часть тестов (одноразовость плана при одновременном захвате — `#91`) держится
на реальном поведении движка (`UPDATE … WHERE consumed_at IS NULL` берёт
блокировку строки), которое ни один самодельный двойник базы не
воспроизводит корректно. Поэтому эти тесты **требуют настоящий Postgres**:

1. `TICKTICK_TEST_PG_DSN` — так работает CI (сервис `postgres:16-alpine`).
2. Иначе — локальный Postgres по unix-сокету.
3. Ни то ни другое не отвечает → пропуск, не падение.

Каждый прогон `pytest` создаёт СЕБЕ отдельную базу
(`ticktick_mcp_test_run<pid>_<rand>`) и сносит её на выходе — так несколько
одновременных прогонов (несколько агентов, соседний worktree) не топчут друг
друга. Подробности и история починки — шапка `tests/pg_helper.py`.

## 4. CI (`.github/workflows/ci.yml`)

Четыре независимые job:

- **test** — поднимает сервис `postgres:16-alpine`, `ruff check .`, затем
  `pytest` с `TICKTICK_TEST_PG_DSN` на этот сервис.
- **guide** — `python scripts/gen_guide.py --check`: `GUIDE.md` обязан быть
  перегенерирован тем же изменением, что меняет описание команды (см. Часть 7
  чек-листа сдачи в `docs/TZ/TZ.md`) — иначе сборка красная.
- **docker** — собирает образ по `Dockerfile`, гоняет `shellcheck` по
  `scripts/*.sh`, парсит все файлы `.github/workflows/*.y*ml` (после
  инцидента 2026-07-22…2026-08-06, когда битый YAML в
  `sync-upstream.yml` молча ронял каждый запуск).

## 5. Деплой на Railway

1. Push в GitHub → Railway: **New Project → Deploy from GitHub repo** (билд
   из `Dockerfile`).
2. Обязательные переменные: `MCP_TRANSPORT=streamable-http`,
   `TICKTICK_ACCESS_TOKEN`, `MCP_SECRET`; опционально `TICKTICK_V2_TOKEN`,
   `TICKTICK_CLIENT_ID`/`_SECRET`. `PORT` инжектит сам Railway — не задавать.
3. Сгенерировать публичный домен (Settings → Networking → Generate Domain).
4. URL сервера: `https://<app>.up.railway.app/mcp/<MCP_SECRET>`.

Railway health-check ходит на `/health` (`railway.toml`). Полная процедура,
включая одно-командный self-deploy (`scripts/setup.sh`) и миграцию со старого
форка — README.md, разделы «Deploy to Railway» и «One-command self-deploy».

**Деплой — только автодеплоем из подключённого репозитория** (`git push` в
`main`). `railway up` не используется никогда — см. правило в CLAUDE.md
владельца.

## 6. Локальная разработка (stdio, для desktop-клиента)

```bash
uv run -m ticktick_mcp.cli auth   # один раз, открывает браузер
uv run -m ticktick_mcp.cli run    # stdio-транспорт
```

Для HTTP-транспорта локально:

```bash
MCP_TRANSPORT=streamable-http MCP_SECRET=dev123 MCP_PORT=8000 \
  uv run -m ticktick_mcp.cli run
```

## 7. Счётчик зарегистрированных команд

`tests/test_tool_registry.py` держит константу `_EXPECTED_TOOLS` и сверяет её
с фактическим числом `@mcp.tool()` в `server.py`. Любая новая/удалённая
команда обязана обновить эту константу тем же коммитом — иначе тест краснеет
осознанно, как страховка от «забыл посчитать».

## 8. Заглушки (test doubles) не имеют права быть добрее сервера

`tests/test_doubles_do_not_cheat.py` — структурная ловушка, не точечная
проверка: она разбирает AST тестовых файлов и ищет признаки того, что
двойник TickTick API исправляет вход (например, переводит служебную строку
`"NONE"` в пустое значение) или что тест достаёт данные путём, которого нет у
настоящего HTTP-клиента (например, читает in-memory реестр планов процесса
вместо ответа тула). Три независимых инцидента, где именно это годами
прятало реальный дефект за зелёными тестами, — в шапке самого файла.

## 9. §13 — Контракт тестового покрытия для гейтованных (two-call) команд

Каждая мутирующая команда, переведённая на форму «один тул, два вызова»
(`_gate_batch`/`_gate_single`, см. `docs/DESIGN_approval_gate.md` §4.2),
обязана иметь тесты минимум на:

1. **Happy path** — call #1 без `manifest_id` строит план и ничего не меняет;
   call #2 с `manifest_id` + правдоподобным `user_reply` исполняет ровно то,
   что было в манифесте.
2. **Refusal path** — call #2 с пустым или отрицательным `user_reply`
   доказывает, что внешний клиент (TickTick) НЕ был тронут — гейт отказал ДО
   любого сетевого вызова.
3. **One-shot edge case** — повторный call #2 с тем же `manifest_id` после
   успешного исполнения отказывает («план уже использован»), а не исполняет
   операцию дважды.

Identity-guard и post-verify — внутренняя логика, перенесённая в `_x_impl`
без изменений, — этим контрактом не покрываются заново, за задокументированными
исключениями (см. `tests/test_tier0_gate_conversion.py`, где две команды —
`attach_file_to_task`, `update_task_comment` — получили дополнительные
`..._plan_identity_guard_*` тесты сверх этого минимума, потому что для них
identity-guard переехал и в фазу построения плана).
