# Ревизия §16 — группа 15 (комментарии + вложения)

Дата: 2026-07-29. Файл: `ticktick_mcp/src/server.py`. Прогнан чек-лист §16
СТАНДАРТА (пп. §3/§4/§5/§6/§7) по: `add_task_comment` (6239-6271),
`update_task_comment` (7032-7073), `delete_task_comment` (7076-7114),
`attach_file_to_task` (6447-6505), `download_task_attachment` (6620-…).

## Классификация read/write методов

Все пять помечены декоратором `@mcp.tool()` **без** `annotations=READONLY`, т.е.
сервер трактует их как write. Для четырёх это верно (add/update/delete comment,
attach_file). Для `download_task_attachment` — **неверно**, см. п.5.

---

### 1. `add_task_comment` (server.py:6239-6271)
- §3 гейт: **❌ ОТСУТСТВУЕТ ПОЛНОСТЬЮ.** Сигнатура не несёт `manifest_id`/
  `user_reply`, вызов мутирует сразу на первом же обращении. Ровно тот
  антипаттерн, о котором предупреждает §3.1 («три разных паттерна гейта в одном
  сервере… как получилось в ticktick-mcp») — здесь просто нулевой паттерн, не
  через `_gate_batch`/`require_consent`. Инвариант §1.2 нарушен без исключений
  «мелкости» не предусмотрено.
- §4 identity-guard: ✅ частично — `_guard_task(task_id, task_title, project_id)`
  сверяет id+название+контейнер, при `mismatch` жёсткий отказ 🛑 (6257-6259).
  При `status=="missing"` (задача не среди открытых) даёт ⚠️ вместо отказа — по
  духу fail-closed (§6) это можно оспорить, но комментирование завершённой задачи
  легитимно, так что решение осознанное.
- §5 post-verify: **❌ ОТСУТСТВУЕТ.** После `add_task_comment` (v2 API) нет
  повторного чтения `get_task_comments`, чтобы подтвердить, что комментарий
  реально появился с тем текстом — просто возвращается «Comment added…» на
  основании самого факта отсутствия исключения (прямое нарушение §5.1.1: «200 OK
  НИКОГДА не является доказательством»).
- §6 fail-closed: не нарушен там, где сработал, но некому срабатывать без гейта.
- §7 формат: ⚠️ ответ на английском («Comment added to '...'»), не по-русски —
  нарушение §7.4 (весь текст, видимый Максиму, ДОЛЖЕН быть по-русски).
- **Вердикт: ❌ блокер.** Нет гейта, нет post-verify, ответ не на русском.

### 2. `update_task_comment` (server.py:7032-7073)
- §3 гейт: **❌ ОТСУТСТВУЕТ** — та же картина: нет `manifest_id`/`user_reply`,
  мутирует немедленно.
- §4 identity-guard: ✅ `_guard_task` с mismatch→🛑 (7052-7054).
- §5 post-verify: ✅ **сделан правильно** — отдельный свежий `get_task_comments`,
  сверка по `comment_id` и по тексту (7060-7067), три исхода по сути (❌ если не
  найден / ❌ если текст не совпал / успех). Лучшая часть этой группы методов.
- §7 формат: ⚠️ смешанный язык — заголовок отказов на русском («🛑 НЕ изменил...»),
  но финальный успех на английском («Comment on '...' updated (проверено).»).
  Непоследовательно и частично нарушает §7.4.
- **Вердикт: ❌ блокер по гейту** (§3), несмотря на образцовый post-verify.

### 3. `delete_task_comment` (server.py:7076-7114)
- §3 гейт: **❌ ОТСУТСТВУЕТ.** Удаление — необратимая операция (комментарий не
  восстановить), и именно для такой операции §1.2 категорически запрещает
  исключение «это же просто...». Сейчас удаление происходит по одному вызову
  без плана и без «да» пользователя.
- §4 identity-guard: ✅ `_guard_task` + доп. проверка существования самого
  `comment_id` перед удалением (7099-7102, честный 🛑 если id устарел/чужой).
- §5.2 pre-snapshot: **❌ отсутствует.** Перед необратимой мутацией текст
  удаляемого комментария нигде не сохраняется (ни в ответе, ни тем более в
  аудит-логе) — после `delete_task_comment` восстановить текст вручную
  невозможно, что прямо противоречит §5.2 («снимок = единственный путь ручного
  отката»).
- §5.1 post-verify: ✅ есть — повторный `get_task_comments`, проверка отсутствия
  id (7105-7108).
- §11 аудит-лог: в файле есть только `deletion_journal.jsonl` для удаления
  **задач** (grep по `_JOURNAL_DIR`/`jsonl`, server.py:2413/2941) — для
  комментариев отдельной записи в audit-лог не найдено. Это отдельный пробел
  §11, общий для всей группы (ни один из пяти методов не пишет в
  append-only журнал).
- §7 формат: ⚠️ снова смесь языков (успех на английском).
- **Вердикт: ❌ блокер** — необратимая мутация без гейта и без pre-snapshot;
  это самый рискованный метод в группе.

### 4. `attach_file_to_task` (server.py:6447-6505)
- §3 гейт: **❌ ОТСУТСТВУЕТ.** Загрузка файла (до 20 МБ, по URL или base64) —
  сразу одним вызовом, без плана/подтверждения.
- §4 identity-guard: ✅ `_guard_task` со свежим `_open_by_id(fresh=True)`
  (6470-6476), mismatch→🛑.
- §5 post-verify: ⚠️ **частичный.** Сверяет только *количество* вложений
  до/после (`pre_count`/`post_count`, 6483/6492-6499), а не имя/размер
  добавленного файла конкретно — по духу §5.1.2 («сверить по полям») это
  слабее, чем у `update_task_comment`. Если на задаче параллельно кто-то ещё
  добавил вложение между pre и post — рост count даст ложный ✅. Также при
  `task_id not in post` честно говорит «вложение не проверить» — это
  корректный ⚠️-путь.
- §7 формат: ⚠️ ответ на английском («Attached '...' (...) to '...'»).
- **Вердикт: ❌ блокер по гейту**, плюс ⚠️ по точности post-verify.

### 5. `download_task_attachment` (server.py:6620-…)
- Классификация read/write: метод делает `GET /api/v1/attachment/...` и отдаёт
  файл как base64 — **не изменяет ничего в TickTick**. Это чистый read по
  определению §0 («Read-метод — только читает, ничего не меняет»).
- **Разбор — попадает ли он под write-требования §3/§4/§5.** Нет: гейт (§3),
  identity-guard-перед-мутацией (§4) и post-verify-после-мутации (§5) по своей
  формулировке применяются к операциям, которые **меняют состояние внешнего
  сервиса**. Скачивание не меняет состояние — гейтить «согласие пользователя»
  на чтение нечем, а post-verify по конструкции требует «перечитать после
  мутации», что здесь бессмысленно (нечего перечитывать — ничего не изменилось).
  Обоснование по аналогии: `get_attachment_download_url` (соседний метод,
  тоже отдаёт доступ к файлу без записи) размечен `READONLY` — значит, сам
  сервер уже трактует «дать доступ к содержимому файла» как read, а не write.
- §2.2 (read не значит безвредный): применимо — метод выносит содержимое файла
  в контекст модели (potentially чувствительные документы). Кап по размеру
  есть (`DOWNLOAD_ATTACHMENT_MAX_BYTES = 15 MB`, 6511) — это ✅ по §10.1.
- **Фактический дефект — не гейт, а аннотация.** Метод объявлен `@mcp.tool()`
  **без** `annotations=READONLY` (6620), хотя по смыслу читает. Это расходится
  с §2.1 («каждый read-метод ДОЛЖЕН нести `readOnlyHint: true`») и создаёт
  разнобой относительно `get_attachment_download_url`, который тот же класс
  операции размечает как READONLY. Раз выбор класса верный (read, не write) —
  единственное расхождение со стандартом здесь: **отсутствующая аннотация**,
  не отсутствие гейта/post-verify (они действительно не нужны).
- **Вердикт: ⚠️ read по существу, но дефект аннотации** — исправление: добавить
  `annotations=READONLY` в декоратор (мелкая, не архитектурная правка).

**Главный вывод:** вся группа write-методов (4 из 5) полностью в обход
`require_consent`/`_gate_batch` — то есть в обход единственной точки входа
гейта, которую §3.1 требует иметь одну на весь сервер («Инструмент, который
мутирует, минуя `require_consent`, — дефект уровня блокер»). Identity-guard и
(местами) post-verify реализованы аккуратно и независимо друг от друга —
явно писались до/вне рефакторинга на единый гейт, который уже применён к
task/project-методам (`plan_task_creation`/`execute_task_creation`,
`delete_tasks`, `restore_tasks` и т.д.). Пятый метод (`download_task_attachment`)
корректно классифицирован как read по существу — требует только правки
аннотации, не архитектурной переделки.
