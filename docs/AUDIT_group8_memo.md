# Аудит группы 8 — create_tasks / plan_task_creation / execute_task_creation

Дата: 2026-07-29. Read-only ревизия по `~/.claude/skills/mcp-development-standard/STANDARD.md`
(§3, §4, §5, §6, §7, §16). Код: `ticktick_mcp/src/server.py`.

## 🔴 Big-ticket: нарушение §3.1 «одна функция, два режима»

`plan_task_creation` (строка 1441) и `execute_task_creation` (строка 1562) — это
ДВЕ разные функции/инструмента, а не один инструмент с режимами plan/execute.
Стандарт (§3.1) прямо требует единой точки входа и называет ЭТОТ САМЫЙ паттерн
в ticktick-mcp примером «трёх разных паттернов гейта в одном сервере» —
дефекта, который стандарт был написан чтобы исправить. Чинить: объединить в
один `@mcp.tool()` с опциональными `manifest_id`/`user_reply` (вызов без них —
план, вызов с ними — исполнение), как уже частично сделано для
declutter/deletion (`plan_task_deletion`/`execute_task_deletion` — тот же
антипаттерн, кстати, тоже нарушает §3.1, но вне текущего скоупа). Это
архитектурная переработка сигнатур — ломает всех потребителей (§12), требует
отдельного обсуждения с Максимом до кода (§15), не мелкая правка.

## Вердикты по методам

### `create_tasks` (строка 1037) — headless-путь, automation_key
- Гейт: корректно отказывает интерактивным вызовам без валидного ключа,
  текст отказа не содержит и не намекает на сам ключ (§8 соблюдён по тексту).
- Сравнение ключа — `hmac.compare_digest(automation_key, SECRET)`, константное
  время — **соответствует §8**.
- **Дефект (существенный):** `automation_key` сравнивается с тем же `SECRET`
  (`MCP_SECRET`), который используется как URL-путь входа в сам сервер
  (`STREAMABLE_PATH = f"/mcp/{SECRET}"`, строка 45) и как ключ подписи
  attachment-ссылок. Это НЕ «отдельный ключ на потребителя» (§8: «Ключ ДОЛЖЕН
  быть отдельным на потребителя… Ротация — заменой env-переменной, без
  правки кода»). Сейчас: (а) все headless-боты используют ОДИН общий секрет —
  отозвать доступ одному без отзыва у всех и без смены URL коннектора
  невозможно; (б) ротация `MCP_SECRET` одновременно меняет URL подключения
  ВСЕХ клиентов И automation_key — риск рассинхрона выше, чем задумано
  стандартом.
- **Дефект:** аудит-лог (`_op_journal`/`_journal_write`, строки 2407-2440) не
  пишет `actor` вообще — ни `human`, ни `automation:<имя>`. §8 требует явной
  пометки automation-записей; §11 требует поле `actor` для КАЖДОЙ мутации.
  Сейчас невозможно постфактум отличить «создано ботом» от «создано интерактивно
  через execute_task_creation».
- Identity-guard на входе (не по id объекта, а по месту назначения) реализован
  через `_guard_project(project_id, exp_proj)` (строка 1148) — приемлемая
  адаптация §4 для create (нет существующего объекта для сверки, есть
  контейнер-назначение).
- Post-verify (строки 1312-1346) — РЕАЛЬНЫЙ: отдельный свежий `_open_by_id(fresh=True)`,
  сверка по `projectId`/`columnId`, отдельно проверяется выживание подзадач.
  Соответствует §5.1.
- **Дефект формата (§7.1):** итоговый текст (`"\n\n".join(parts)`, строка 1361)
  НЕ имеет обязательного `### <эмодзи> <заголовок>` первой строкой. Собирается
  из кусков «Создано N:\n…», «Проверка назначения:\n…», «Ошибки (N):\n…» без
  единого хелпера-обёртки и без ведущего статус-эмодзи — нарушает §7.1 п.1,5 и
  §7.5 (единый хелпер на репозиторий).

### `plan_task_creation` (строка 1441) — read-only планирование
- `annotations=READONLY` проставлена — соответствует §2.1.
- Манифест НЕ мутирует, честно только строит план — §3.1 (по существу
  read-фазы) соблюдён.
- Кап `max_items` с явным отказом при превышении — соответствует §10.1.
- Манифест **не содержит `object_hash`** (в отличие от delete/declutter
  манифестов, строки 2197/2518/2637/4113/4127). Для create это архитектурно
  объяснимо — объекта, чьё состояние могло «уехать» между планом и
  исполнением, ещё не существует, — но при объединении в §3.1-совместимую
  форму (`require_consent`) это стоит явно задокументировать как осознанное
  исключение, а не молчаливый пропуск проверки.
- Duplicate-radar (проверка на дубли заголовков в проекте назначения) — хорошая
  практика сверх минимума стандарта, не входит в §3.3, но полезна.

### `execute_task_creation` (строка 1562)
- Проходит через `_require_consent(action="create", tier=1, ...)` —
  единственная точка входа для проверок §3.3 соблюдена *локально* (хотя
  архитектурно это вторая функция, см. big-ticket пункт выше).
- **Докстринг лжёт о поведении (§7.4, блокер):** строки 1462-1464 в
  `plan_task_creation` утверждают «execute_task_creation does not hard-block
  on user_reply the way the deletion/declutter tools do». Фактически
  `_require_consent` при `tier=1` (строка 2363: `if tier <= 0: return True` —
  единственный тир без гейта) проходит ТЕ ЖЕ проверки §3.3, что и `tier=2`:
  `_is_negative_reply`/`_is_affirmative_reply` обязательны, пустой/отрицательный/
  похожий-на-эхо `user_reply` **отказывается** (строки 2383-2391) — то есть
  гейт для create жёсткий, ровно как для delete. Докстринг вводит модель в
  заблуждение о том, что можно быть менее строгим с подтверждением при
  создании — прямое нарушение §7.4 («докстринг… НИКОГДА не врёт о
  поведении… дефект уровня блокера»). Чинить: либо привести код к
  описанному поведению (снять часть проверок для tier=1, если это
  осознанное решение Максима — тогда нужно √ его одобрение по §15), либо (что
  вероятнее корректно) поправить текст докстринга, убрав ложное «does not
  hard-block».
- TTL/one-shot/anti-duplicate-gap (`_MANIFEST_TTL`, `consumed`, `MIN_CONSENT_GAP`)
  — реализованы и переиспользуются из общего `_require_consent` — соответствует
  §3.3 п.1,4,5.
- Post-verify приклеивается сервером тем же ходом (`_build_operation_report`,
  строки 1594-1596) — соответствует §5.1.4 (не «вызови отдельно»).
- Тот же дефект формата §7.1, что и у `create_tasks` (нет `###`-заголовка).

## Итог
- Блокер: `create_tasks`/`plan_task_creation`/`execute_task_creation` —
  архитектурное расхождение с §3.1 (две функции вместо одной с режимами) —
  требует обсуждения с Максимом до правки (§15), затрагивает весь сервер, не
  только эту тройку.
- Блокер: докстринг `execute_task_creation`/`plan_task_creation` лжёт о
  «мягком» гейте создания (§7.4).
- Существенно: `automation_key` = `MCP_SECRET` (не отдельный ключ на
  потребителя, §8); аудит-лог не пишет `actor` (§8, §11).
- Средне: формат ответа не следует каркасу §7.1 (нет `###`-заголовка,
  собирается вручную, не хелпером).
- В порядке: константное сравнение ключа, отсутствие утечки ключа в
  ошибках/логах, identity-guard на назначение при create, реальный
  post-verify с раздельным свежим чтением, капы на batch, TTL/one-shot
  манифестов, склейка отчёта сервером.
