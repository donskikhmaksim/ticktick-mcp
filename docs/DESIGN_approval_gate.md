# DESIGN: гейт подтверждения на in-chat «да» (версия 2 — без кнопок)

Проектный документ (только дизайн, код не менялся). Версия 2 — **переписана
2026-07-27** по прямому требованию Максима: решение должно работать на его
ОБЫЧНОМ «да» В ЧАТЕ. **Без кнопок, без Telegram, без ввода кодов вручную, без
внеполосных каналов.** Прежний дизайн v1 (Telegram-nonce / inline-кнопка) —
**ОТВЕРГНУТ пользователем** и сохранён ниже только как исторический контекст в §7.

Основа: аудит `docs/PIPELINE_ticktick_mcp.md` и таксономия
`docs/DESIGN_write_tool_taxonomy.md` (8 инструментов 🔴, 12 🟡, 15 🟢).

Термины для не-программиста:
- **Гейт** — проверка в КОДЕ сервера, которая физически не даёт применить
  изменение, пока условие не выполнено.
- **Модель** — Claude, ведущий диалог и вызывающий инструменты.
- **User turn (ход пользователя)** — реальное сообщение Максима в чате. **Модель
  его не создаёт** — оно приходит от человека через клиент (claude.ai). Это
  единственный элемент разговора, который модель не может сфабриковать.
- **Elicitation** — механизм MCP, где СЕРВЕР просит клиента показать
  пользователю форму/вопрос вне контекста модели, и ответ идёт серверу мимо
  модели.


## 0. TL;DR

1. **Elicitation в claude.ai не поддерживается** (на июль 2026). Он есть в Claude
   Code, но для веб-клиента claude.ai коннекторов — нет; запрос
   `anthropics/claude-ai-mcp#153` (открыт 6 апр 2026) всё ещё OPEN. Максим
   подключает сервер как custom connector по URL → **закладываться на
   elicitation нельзя.** (§1)

2. **Теорема невозможности (честно и сразу):** при ограничениях {только чат, без
   кнопок, без внеполосного канала, без elicitation} **криптографически жёсткого,
   модель-независимого гейта не существует.** Любой секрет, который сервер может
   передать в чат, модель прочитает; сервер не видит границы ходов и не может
   доказать, что между планом и исполнением был реальный ход человека. (§2)

3. **Правильный сдвиг рамки:** реальный противник здесь — **не злонамеренная
   модель, подделывающая согласие**, а **спешащая/автономная модель, которая
   само-подтверждает по инерции** (сегодня `execute` можно вызвать сразу после
   `plan`, потому что пароль `DELETE N` сервер сам же и напечатал). Значит цель —
   сделать так, чтобы **правдивое поведение было путём наименьшего сопротивления,
   а само-подтверждение требовало явной лжи**, которую неадверсариальная модель
   не совершает. (§3)

4. **Рекомендуемый механизм (без кнопок): `plan → показ плана → «да» в чате →
   execute с дословной ретрансляцией согласия».** `plan_*` НЕ печатает
   детерминированный `CREATE N`/`DELETE N`. `execute_*` вместо пароля принимает
   `user_reply` — **дословную последнюю реплику пользователя**, и сервер:
   (а) проверяет, что реплика непустая и утвердительная (server-side словарь
   да/yes/подтверждаю/удаляй…); (б) требует минимального зазора по стенным часам
   между показом плана и execute (ловит «выстрел дуплетом» в один ход);
   (в) манифест одноразовый, с TTL и привязкой к хешу объектов. Всё это — через
   ЕДИНУЮ функцию `_require_consent()`, покрывающую всю пишущую поверхность. (§4)

5. **Остаточный риск:** модель может сфабриковать `user_reply="да"`. Это НЕ
   закрывается в рамках заданных ограничений. Принимается как приемлемый
   компромисс, потому что (i) модель на практике неадверсариальна, (ii) поле
   `user_reply` превращает тихий обход в явную ложь и логируется для пост-аудита,
   (iii) единственные способы закрыть это (OOB-nonce/кнопка/elicitation) прямо
   отвергнуты Максимом или площадкой. (§4.5)

6. **UX:** гейт только на 8 опасных/необратимых инструментах (🔴 из таксономии),
   лёгкое подтверждение — на 12 🟡, ноль гейта — на 15 🟢. Ноль кнопок, ноль
   лишних действий: единственное, что делает Максим, — пишет обычное «да» на
   показанный план. (§5)

7. `automation_key` (headless-бот/n8n) — **не трогаем.** (§6.4)


## 1. Факт про elicitation на claude.ai (проверено, июль 2026)

Проверка задачи п.1: поддерживает ли клиент claude.ai server-initiated
elicitation.

**Вывод: НЕТ, на июль 2026 не поддерживает / не гарантирует.**

- Elicitation **реализован в Claude Code**, но для **claude.ai (веб-приложение и
  коннекторы) — нет**. Публичный запрос на добавление —
  `github.com/anthropics/claude-ai-mcp` issue **#153** (открыт **2026-04-06**,
  label *enhancement*, статус **OPEN** на момент проверки 2026-07-27). Цитата из
  issue: *«With Elicitation now supported in Claude Code, support in Claude.ai as
  well would help finally make this feature of the spec something MCP server
  developers could rely on.»* — т.е. авторы MCP-серверов пока НЕ могут на него
  полагаться на claude.ai.
- Единственная разновидность elicitation, которую площадка практикует, —
  **URL-mode** (увести пользователя на доверенный внешний URL для OAuth / ввода
  реквизитов / оплаты). Это не наш кейс: (а) это внешняя страница = фактически
  кнопка/OOB, что Максим отверг; (б) form-mode elicitation (структурный вопрос
  внутри клиента, ответ мимо модели) — как раз то, что #153 и просит, и чего нет.
- Максим подключает сервер как **custom connector по URL**
  (`https://<app>.up.railway.app/mcp/<MCP_SECRET>`, README:203-205) на
  Pro/Max-плане. Никакой гарантии, что этот путь получит server-initiated
  form-elicitation, нет.

**Следствие:** «идеальный без-кнопок, in-chat, модель-независимый путь» через
elicitation сейчас недоступен. Держим его как **целевую миграцию (§6.5, фаза 3)**
на случай, когда #153 закроют, но основной механизм строим без него.

> Если/когда claude.ai включит form-mode elicitation — это СРАЗУ становится
> рекомендованным механизмом: сервер спрашивает «Удалить N задач?
> [подтвердить/отмена]», клиент показывает это вне контекста модели, ответ
> приходит серверу мимо модели. Это единственный путь, дающий и «без кнопок в
> нашем смысле» (нативный диалог клиента, а не наш UI), и настоящую
> модель-независимость. До тех пор — §4.


## 2. Почему in-chat «да» нельзя сделать криптографически жёстким (теорема невозможности)

Зафиксируем честно, чтобы больше не возвращаться.

Модель угроз (из v1, остаётся в силе):
> Всё, что сервер вернул в тексте результата инструмента, модель ЗНАЕТ. Сервер
> общается с моделью ТОЛЬКО через текст tool-result; обратно — только через
> аргументы tool-call.

Отсюда три невозможности при заданных ограничениях:

1. **Секрет спрятать нельзя.** Любой одноразовый код, который сервер положит в
   ответ `plan_*`, модель прочитает и сможет сама передать в `execute_*`. Спрятать
   код можно ТОЛЬКО во внеполосный канал (Telegram/страница/почта) — все они
   отвергнуты Максимом (без кнопок/без Telegram) либо скомпрометированы (Gmail-MCP,
   notes_read — подключены к той же модели).

2. **Границу хода сервер не видит.** Проверка задачи п.2: «есть ли доступный
   серверу сигнал о смене хода?» — **НЕТ.** В протоколе MCP-коннектора сервер
   получает только JSON-RPC `tools/call`. Базовая спека не содержит уведомления
   «пришёл новый user turn»; claude.ai такого сигнала серверу не шлёт. Значит
   «вооружать манифест только на новом ходу пользователя» **напрямую
   нереализуемо** — сервер физически не знает, был ли между `plan` и `execute`
   ход человека. (Ближайшие доступные прокси — таймер и ретрансляция реплики, §4.)

3. **Ход пользователя подделать нельзя — но и ПРОЧИТАТЬ его наличие сервер не
   может.** Опорная мысль Максима верна: настоящее «да» приходит как реальное
   сообщение, которого модель не создаёт. Но это свойство живёт на уровне
   транскрипта КЛИЕНТА, а не доходит до сервера. Сервер видит лишь то, что модель
   решила положить в аргумент вызова. Поэтому «наличие реального да» — сигнал,
   доступный клиенту/человеку, но НЕ серверу напрямую.

**Итог §2:** жёсткий гейт = либо спрятанный от модели секрет (нужен OOB —
отвергнут), либо серверный сигнал о ходе (нет в протоколе), либо elicitation (нет
на claude.ai). Все три пути закрыты. Значит на in-chat «да» строим **не
криптографический, а поведенческий гейт** — максимально надёжный в рамках того,
что осталось. Это не слабость дизайна, а граница площадки; фиксируем её явно.


## 3. Смена рамки: реальный противник — спешащая модель, а не лжец

Ключевое наблюдение, которое делает поведенческий гейт осмысленным:

- Модель на площадке Максима **неадверсариальна**. Она не пытается злонамеренно
  подделать согласие; она иногда **торопится** — в автономном/многозадачном
  режиме вызывает `execute` сразу за `plan`, потому что сегодня для этого есть всё
  необходимое: пароль `DELETE N` сервер сам напечатал в ответе `plan`.
- Значит опасен именно **путь наименьшего сопротивления**: сейчас тихое
  само-подтверждение проще, чем дождаться человека. Пароль `DELETE N` — это
  контрольная сумма, которую модель считает из СВОИХ данных, вообще не
  обращаясь к пользователю.

**Цель дизайна (формулируем как инвариант):**
> Сделать так, чтобы `execute` НЕЛЬЗЯ было корректно вызвать, не совершив
> действия, которое (а) требует наличия реальной реплики пользователя как
> входных данных, и (б) при отсутствии такой реплики превращается в явную ложь,
> которую неадверсариальная модель не произносит; плюс структурно затруднить
> «дуплет» plan+execute в один ход.

Это не даёт математической гарантии (§2), но переносит поведение с «тихий обход =
дефолт» на «обход = осознанная фабрикация + оставленный в логе след». Для
неадверсариальной модели это на практике эквивалентно гейту.


## 4. Рекомендуемый механизм: plan → показ → «да» → execute(user_reply)

Механизм без кнопок, целиком на обычном «да» в чате.

### 4.1 Поток

```
1. Пользователь: «удали эти 5 задач»
2. Модель → plan_task_deletion(...)          [read-only, строит манифест]
3. Сервер: манифест сохранён, state=AWAITING_CONSENT, plan_shown_at=now,
           object_hash=sha256("delete|id1,id2,...")
   Ответ plan_*: показывает ПОЛНЫЙ план (что удаляем) + инструкцию:
     «План готов. Покажи его пользователю дословно и дождись явного «да».
      Когда пользователь подтвердит — вызови execute_task_deletion(manifest_id,
      user_reply=<дословная последняя реплика пользователя>). НЕ вызывай execute
      в этом же ответе.»
   ⚠ НЕТ строки confirm="DELETE 5". Детерминированного пароля больше нет.
4. Модель показывает план пользователю. [конец хода модели]
5. Пользователь: «да»                         [реальный user turn]
6. Модель → execute_task_deletion(manifest_id, user_reply="да")
7. Сервер _require_consent() проверяет (§4.3). Ок → удаляет. Иначе → отказ.
```

### 4.2 Что меняется в сигнатурах

- `plan_*` — остаются read-only, но **из вывода убирается** строка
  `confirm="CREATE N"` / `DELETE N` / `DECLUTTER N`. Вместо неё — текстовая
  инструкция «дождись да, потом execute с user_reply».
- `execute_*` — параметр `confirm` заменяется (или дополняется) на:
  - `manifest_id: str`
  - `user_reply: str` — **дословная последняя реплика пользователя**. Докстринг:
    «Скопируй сюда ДОСЛОВНО последнее сообщение пользователя, которым он
    подтвердил. Не сочиняй: если пользователь ещё не ответил — не вызывай этот
    инструмент.»
- `set_declutter_decision` — перестаёт принимать `decision="approved"` от модели
  напрямую; одобрение строк идёт через тот же `_require_consent()` с `user_reply`
  (§6.2).

### 4.3 Серверные проверки `_require_consent()`

Для Тир-🔴/🟡 (Тир-🟢 пропускается сразу):

1. **Манифест валиден:** существует, `state==AWAITING_CONSENT`, не `consumed`,
   не истёк (TTL). Иначе — «план не найден/истёк, вызови plan заново».
2. **Привязка (binding):** пересчитать `object_hash` из текущего набора объектов
   и сравнить с сохранённым. Защита от переигрывания кода на другой план.
3. **Утвердительность реплики:** `user_reply` непустая и матчится по
   server-side словарю утверждения (да, ага, ок, окей, подтверждаю, удаляй,
   давай, yes, confirm, го, +). Отрицания (нет, стоп, отмена, погоди, cancel) →
   **жёсткий отказ** и инвалидция манифеста. Строки, похожие на служебные
   («DELETE 5», имя инструмента, JSON) → отказ (это не человеческое «да»).
4. **Минимальный зазор (anti-дуплет):** `now - plan_shown_at >= MIN_CONSENT_GAP`
   (env, для 🔴 по умолчанию ~2-3 сек; для 🟡 — 0). Ловит случай «модель
   выстрелила plan и execute в один ход, не отдав слово человеку». Слабая, но
   дешёвая эвристика; при срабатывании — «покажи план и дождись ответа
   пользователя, потом повтори execute».
5. **Одноразовость:** после успеха `consumed=True`, `state=DONE`.
6. **Лог:** записать в `deletion_journal.jsonl` факт + `user_reply` дословно +
   `object_hash` + тайминг (для пост-аудита; сырых секретов нет, писать безопасно).

### 4.4 Почему это лучший из достижимых без кнопок

- **Наличие реплики требуется как ВХОД.** Сегодня `DELETE N` модель берёт из
  своих данных, не обращаясь к человеку. Теперь корректный вызов требует
  подставить реальную реплику пользователя — а если её нет, честной модели
  нечего туда положить.
- **Тихий обход превращён в явную ложь.** Чтобы обойти, модель должна СОЧИНИТЬ
  `user_reply="да"`, которого не было. Для неадверсариальной модели это резкий
  барьер: инструкция прямо запрещает выдумывать реплику, и след остаётся в логе.
- **«Дуплет» структурно затруднён** таймером §4.3.4 + инструкцией «не вызывай
  execute в этом же ответе».
- **Единая точка.** Через `_require_consent()` проходит ВСЯ пишущая поверхность —
  согласие перестаёт зависеть от того, есть ли у инструмента текст в докстринге.

### 4.5 Остаточный риск (честно)

- **Главный остаточный риск:** модель фабрикует `user_reply="да"` без реального
  хода пользователя. **Это НЕ закрывается** при ограничениях {без кнопок, без OOB,
  без elicitation} — см. теорему §2. Принимаем как компромисс: модель
  неадверсариальна; поле логируется; альтернативы отвергнуты пользователем.
- **Соблазн уговора.** Верно для любой схемы согласия: модель может уговорить
  человека сказать «да». Не решается технически.
- **Ложные срабатывания таймера** (быстрый человек). Для 🔴 приемлемо: лучше «не
  удалил, повтори» чем «удалил без паузы». Порог настраиваемый.
- **Fail-closed при неоднозначности:** если `user_reply` пуст/отрицателен/похож
  на служебную строку — отказ, а не «на всякий случай выполнить».


## 5. Политика «кому нужен гейт» (по таксономии, ноль лишних действий)

Опираемся на `DESIGN_write_tool_taxonomy.md`. Гейт — только там, где он оправдан;
на мелком обратимом — ничего, чтобы Максим не делал лишних «да».

- **Тир 🟢 — без гейта (16 инструментов):** `create_tasks`,
  `execute_task_creation`, `create_subtask`, `duplicate_task`, `checkin_habit`,
  `create_project`, `create_project_column`, `create_project_group`,
  `delete_project_group`, `move_project_to_group`, `create_tag`,
  `add_task_comment`, `update_task_comment`, `attach_file_to_task`,
  `download_task_attachment`, `unset_task_parent`. `_require_consent()` их
  пропускает. Здесь гейт только мешает.
  **`unset_task_parent`** — ИСПРАВЛЕНО (было ошибочно перечислено в 🟡 ниже, а
  в коде гейта не было НИКОГДА; см. PLAN_retrofit.md пакет 13, п.13.2,
  подтверждено Максимом 2026-07-29, Вариант B): асимметрия с зеркальной
  `set_task_parent` (та в 🟡) осознанная — вложение под НЕ ТОГО родителя
  рискует потерять контекст среди чужих подзадач, а отцепление всегда идёт в
  одно известное конечное состояние («стать задачей верхнего уровня»); риск
  «не той задачи» закрывает identity-guard, а не диалог подтверждения.
- **Тир 🟡 — лёгкое подтверждение (11):** `update_tasks`, `complete_tasks`,
  `move_tasks`, `set_task_parent`, `set_task_tags`,
  `abandon_task`, `update_project`, `archive_project`, `delete_tag`,
  `delete_task_comment`, `restore_tasks`. Тот же `_require_consent()`, но
  `MIN_CONSENT_GAP=0` и допускается упрощённый путь: показать однострочный
  эффект + принять `user_reply` без строгого манифеста (для не-манифестных
  инструментов — inline-подтверждение через тот же валидатор утверждения). Можно
  завязать на порог количества (`update_tasks`/`move_tasks`/`complete_tasks` выше
  N объектов → как 🔴).
- **Тир 🔴 — гейт всегда (8):** `delete_tasks` (в т.ч. одиночное — сейчас идёт
  без confirm!), `execute_task_deletion`, `delete_task_with_subtasks` (уже
  no-op-редирект), `execute_declutter`, `resume_declutter`,
  `set_declutter_decision`, `delete_project`, `rename_tag`(ветка слияния — уже

## 6. Единый механизм и план реализации для Sonnet

### 6.1 Единая точка — `_require_consent()`

Ввести один внутренний помощник (НЕ новый MCP-инструмент), через который проходят
ВСЕ пишущие вызовы. Файл: `ticktick_mcp/src/server.py`.

```python
def _require_consent(
    *,
    action: str,            # "delete" | "update" | "declutter" | ...
    objects: list[str],     # id объектов — для object_hash
    tier: int,              # 0=🟢, 1=🟡, 2=🔴
    manifest_id: str | None,
    user_reply: str | None,
    automation_key: str = "",
) -> ConsentResult:         # .ok: bool, .reason: str
    ...
```

Логика:
- `automation_key` валиден (HMAC) → пропуск (headless-обход, §6.4).
- `tier == 0` → пропуск.
- `tier >= 1` → проверки §4.3: манифест (если есть) валиден и не истёк,
  `object_hash` совпадает, `user_reply` утвердительна, зазор соблюдён, one-shot.
  Иначе `ok=False` с человекочитаемой причиной-инструкцией.

Это убирает разнобой «у одного инструмента текст-напоминание, у другого нет».

### 6.2 Миграция plan/execute и дыр

### 6.3 Свести три пути создания к одному решателю

`create_tasks`(HMAC) / `create_subtask`(:4361, без текста) /
`duplicate_task`(:5817) — все 🟢, но пропустить через `_require_consent(tier=0)`

Классификация не меняется (создание обратимо), меняется единообразие.

### 6.4 Fallback / деградация

- `MIN_CONSENT_GAP`, словарь утверждения — env-настраиваемы.
- **Нет старого echo-фолбэка.** Строку `confirm="… N"` убираем везде — иначе
  смысл теряется (модель снова само-подтвердит).
- `automation_key` (бот/n8n, :760/:833, `hmac.compare_digest`) — **не трогаем**:
  осознанный headless-обход, проходит `_require_consent` по ветке automation_key.

## 7. Приложение: почему v1 (Telegram-nonce / кнопка) отвергнут

Для истории. v1 рекомендовал прятать одноразовый nonce во внеполосный канал
(Telegram-пуш) или ставить серверный флаг через inline-кнопку бота. С точки
зрения криптостойкости это **строго сильнее** механизма §4 (даёт настоящую
модель-независимость: секрет модель не видит / нужно физическое нажатие).

**Максим отверг это прямо:** «моё согласие в чате должно работать; без кнопок».
Требование — обычное «да» в чате, без Telegram, без ввода кодов, без переключения
на телефон. При этом ограничении §2 доказывает, что жёсткого гейта не остаётся, и
§4 — лучший достижимый компромисс. v1 сохраняется в git-истории как «аварийный
максимум надёжности», если Максим когда-нибудь снимет ограничение на OOB-канал;
до тех пор он не реализуется.
