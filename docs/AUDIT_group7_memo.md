## `operation_report` — отдельный тщательный разбор (server.py:2910-2997, движок `_build_operation_report`)

Это read-инструмент, но по факту — единственный механизм post-verify (§5) для
**всех** write-методов сервера: используется не только напрямую (2933), но и
приклеен сервером в ответ `execute_declutter`/batch-операций напрямую
(server.py:1596, 2806, 3948, 4323) — т.е. дефект здесь бьёт по каждому
write-инструменту, а не только по вызовам `operation_report` явно.

**Что сделано правильно:**
- §5.1.1: ✅ отдельный свежий запрос — `_open_by_id(fresh=True)` перечитывает
  живое состояние заново, не переиспользует тело мутации (server.py:2958).
- §5.1.3: ✅ `200 OK` нигде не трактуется как доказательство — весь `_verify_item`
  сверяет **поля** живого объекта с ожидаемыми (server.py:2849-2907).
- §5.1.4: ✅ склейка сервером — отчёт прикрепляется самим сервером к ответу
  write-инструментов (см. места использования выше), а не «вызови отдельно».
  Явная директива для модели «перепечатай ДОСЛОВНО» тоже на месте (2992-2993).
- Устойчивость к недоступности сервиса: ✅ если `_open_by_id(fresh=True)`
  вернул `None` — сразу честный общий ⚠️ «живое состояние недоступно, исход НЕ
  ПОДТВЕРЖДЁН» (2959-2963), не выдаёт ложный ✅.
- `_verify_item` для `delete`/`restore`/`complete`/`abandon`/`create`/`move`/
  `tags`/`parent`/`update`/`delete_project` — сверяет честно по фактам, не по
  «похоже на то, что просили»: например `create` явно показывает, куда РЕАЛЬНО
  попала задача, даже если запрос был противоречивым (2859-2861 — комментарий в
  коде прямо формулирует эту философию верно).

**Реальные расхождения со стандартом:**

1. **❌ Тройной исход не считается честно в итоговой сводке (§5.3).** Функция
   считает только `ok`/`bad` (server.py:2973, 2986-2989) — счётчика ⚠️ **нет
   вообще**. `_verify_item` умеет возвращать ⚠️ (ветка `delete_project` при
   неудачной перечитке списка проектов, server.py:2839-2842), но в
   `_build_operation_report` это ⚠️ не попадает ни в `ok`, ни в `bad` — просто
   выпадает из итога. Результат: строка «**Итог: ✅ 2 подтверждено, ❌ 0
   расхождений.**» может появиться, когда по факту был 1 непроверенный пункт —
   тело отчёта его покажет строкой, но итоговая сводка **не отражает** этот факт
   числом, и сумма `ok + bad` тихо не равна числу проверенных пунктов. Это прямое
   нарушение требования §5.3 «три и только три исхода» — по факту исход есть, а
   учёта нет. Для механизма, который призван быть источником правды, это
   значимая дыра: агент/Максим, бегло глядя на «Итог», может пропустить
   единственную непроверенную строку в теле.
   **Как чинить:** завести `warn = 0`, инкрементить по `"⚠️" in head`, и
   печатать «Итог: ✅ N подтверждено, ⚠️ M не проверено, ❌ K расхождений.»
   всегда тремя числами, даже если M/K = 0 — так пропажа физически не может
   остаться незамеченной.

2. **⚠️ Мёртвый, но опасный fallback использует запрещённый ASCII-символ
   (§7.2).** Последняя строка `_verify_item` (server.py:2907):
   `return f"- ✓ **«{title}»» — записана в журнал (тип {op} не проверяется
   автоматически)"` — использует `✓` (ASCII/обычная галочка), которую §7.2
   прямо запрещает как статус-символ («ASCII-варианты (✓, ✗) НИКОГДА не
   используются как статус»). Сейчас это недостижимая ветка: докстринг
   `_op_journal` фиксирует замкнутый набор `op ∈ create/update/complete/delete/
   move/tags/parent/abandon` (2431), и все восемь плюс `restore`/`delete_project`
   явно обработаны выше в `_verify_item` — так что живых записей с
   неизвестным `op` в журнале сегодня нет. Но это тихая мина: если
   когда-нибудь добавится новый `op` без параллельного обновления
   `_verify_item` (например через `plan_declutter`/будущий write-метод),
   отчёт по нему молча получит некорректный по легенде символ **и** (из-за
   находки №1) не попадёт в итоговый счёт вообще — то есть новый тип мутации
   получит отчёт, который выглядит нейтрально, а не как ⚠️/отказ. Правильное
   поведение по духу §6 (fail-closed) — на неизвестный `op` возвращать ⚠️ с
   явным «этот тип операции не покрыт post-verify», а не тихий ASCII-плейсхолдер.

3. Докстринг `operation_report` (2911-2929): ✅ честный, не обещает того, чего
   нет («re-checks every item against the CURRENT live state») — но не
   упоминает находку №1 (что итоговая сводка может занижать число
   непроверенных пунктов). Это не «докстринг врёт», но и не полная картина;
   после фикса №1 упоминать не нужно будет вовсе, т.к. дыра закроется.

4. Формат (§7): ✅ заголовок `### 🧾 Независимый отчёт` соответствует
   зафиксированному в легенде §7.2 назначению эмодзи 🧾 («заголовок независимой
   проверки») и шаблону §5.3. Язык — по-русски, полностью соответствует §7.4.

**Вердикт по `operation_report`/`_build_operation_report`: ⚠️→❌ не «просто
мелкая недоделка».** Механизм в целом спроектирован честно и структурно
правильно (свежий запрос, сверка по полям, склейка, явный текст «не
пересказывай»), но **сам критический показатель доверия — итоговая цифра —
может занижать степень непроверенности**, что подрывает единственную вещь, ради
которой этот инструмент существует: дать Максиму факт, а не оптимистичный
пересказ. Требует правки (находка №1 — по существу; находка №2 — защитный
фикс на будущее, до появления нового `op`).
