# Полная карта механики всех методов ticktick-mcp

Источник истины: `ticktick_mcp/src/server.py` на `main`, коммит `ea3f839`
(гейт v2 + фикс дат `_sync_point_date` + identity-guard на `delete_project`).
Старые доки (`docs/PIPELINE_ticktick_mcp.md`, `docs/DESIGN_*`) НЕ использовались
как источник фактов — только код. Всего разобрано **78** `@mcp.tool()`.

## Как читать гейты (подтверждения)

- 🔴 **Реальный гейт** — метод вызывает `_require_consent(tier>=1, ...)`, и
  без НАСТОЯЩЕГО `user_reply` (проверяется на «да»/«нет»/пустоту/эхо
  манифеста функциями `_is_affirmative_reply`/`_is_negative_reply`) сервер
  физически откажет — вернёт `🛑` и ничего не сделает. Это единственная
  категория, где код, а не текст докстринга, останавливает выполнение.
- 🟡 **Только протокол в докстринге** — в тексте написано «покажи
  пользователю и дождись да», но КОД никакого `_require_consent` не вызывает
  и выполнит операцию, даже если модель ничего не показала и придумала
  согласие. Это соглашение с моделью (Claude), а не серверная защита.
- 🟢 **Без подтверждения** — выполняется сразу; либо потому что действие
  дешёвое/обратимое (создать тег, добавить комментарий), либо это
  read-only метод.

Отдельно — **identity-guard** (защита «не та задача/проект»): почти каждый
пишущий метод перед мутацией сверяет переданный id с ЖИВЫМ состоянием
TickTick (`_guard_task`/`_guard_project`/`_split_tasks_by_state`) — если id
достаётся до другой задачи/проекта (не совпадает переданное название), метод
ОТКАЗЫВАЕТ, а не выполняет вслепую. Это работает независимо от гейта
согласия и есть почти везде ниже — отмечаю отдельно только где его НЕТ или
где он специфичен.

**post-verify** — сделал ли сервер отдельное, независимое чтение живого
состояния TickTick ПОСЛЕ операции и сравнил с тем, что просили. Отдельно —
есть ли **journal + `operation_report`**: полноценная пишущая операция
получает `record_id`, кладётся в файл-журнал (`/data/deletion_journal.jsonl`)
и позже можно вызвать `operation_report(record_id)` — это НЕЗАВИСИМАЯ от
модели проверка (сервер сам перечитывает TickTick). Многие мелкие write-методы
делают inline-проверку (перечитали и сверили в этом же вызове), но НЕ пишут в
журнал — значит `operation_report` по ним позже вызвать нельзя, доказательство
есть только в тексте текущего ответа.

## 1. Чтение задач и проектов

Общий паттерн: все read-only, аннотированы `READONLY` (Claude может не
спрашивать разрешения на вызов вообще). Ничего не гейтится и не журналится —
гейтить нечего, это чтение. Часть методов идёт через официальный API
(`ticktick`, по одному проекту за раз), часть — через `ticktick_v2`
(единый sync-снимок, быстрее и включает Inbox, которого нет в официальном
списке проектов). Где `ticktick_v2` не настроен (нет `TICKTICK_V2_TOKEN`),
методы либо возвращают отказ («requires v2 API»), либо тихо падают на
официальный API с оговоркой в докстринге, что тогда Inbox не виден.

- **get_projects** — список всех проектов. 🟢. Официальный API.
- **get_project** — детали одного проекта по id. 🟢.
- **get_project_tasks** — все задачи одного проекта. 🟢.
- **get_task** — детали одной задачи по paре project_id+task_id. 🟢.
- **get_all_tasks** — вообще все открытые задачи по всем проектам + Inbox
  одним вызовом (предпочитает v2 sync-состояние). 🟢.
- **get_tasks_by_priority** — фильтр по приоритету (0/1/3/5). 🟢.
- **get_tasks_due_today** / **get_overdue_tasks** / **get_tasks_due_tomorrow**
  / **get_tasks_due_in_days** / **get_tasks_due_this_week** — фильтры по
  сроку, используют местную таймзону (`_USER_TZ`) и учитывают фикс #36
  (all-day дедлайн сравнивается как «голая» календарная дата, не пересчитывается
  через часовой пояс, иначе при отрицательном смещении дата съезжала на день
  назад). 🟢.
- **search_tasks** — поиск по названию/содержимому/подзадачам (простая
  подстрока), только открытые. 🟢.
- **get_recurring_tasks** — задачи с правилом повтора (`repeatFlag`), опционально
  фильтр текстом. 🟢.
- **get_engaged_tasks** / **get_next_tasks** — GTD-подобные умные фильтры
  (высокий приоритет/срок сегодня/просрочено vs средний приоритет/завтра). 🟢.
- **get_completed_tasks** — последние завершённые (requires v2). 🟢.
- **list_tags** — список тегов (requires v2). 🟢.
- **get_tasks_by_tag** — задачи с конкретным тегом (requires v2). 🟢.
- **get_inbox_tasks** — открытые задачи в Inbox (requires v2). 🟢.
- **list_filters** — сохранённые smart-list фильтры (requires v2). 🟢.
- **run_filter** — выполнить сохранённый фильтр по имени/id (requires v2). 🟢.
- **list_project_groups** — список групп/папок проектов (requires v2). 🟢.
- **get_task_comments** — комментарии к задаче, включая id (нужен для
  update/delete комментария) (requires v2). 🟢.
- **get_statistics** — очки достижений/уровень/счётчики завершённого
  (requires v2). 🟢.
- **get_trash** — недавно удалённые задачи (requires v2), нужен для
  `restore_tasks`. 🟢.
- **list_task_attachments** — вложения задачи (имя/id/размер), объединяет
  структурные метаданные и ссылки, вшитые в текст задачи (requires v2). 🟢.
- **search_all_tasks** — расширенный поиск: scope (открытые/закрытые
  проекты/оба), режим match (подстрока/целое слово), поле (title/content/оба),
  опционально медленный поиск по комментариям (по одному запросу на задачу, с
  капом в 150 запросов). 🟢.
- **get_task_info** — полная карточка задачи: все поля, чеклист, подзадачи,
  вложения, кто создал/когда изменено (requires v2). 🟢.
- **get_task_activity** — журнал изменений конкретной задачи (кто/что/когда) —
  реальный endpoint `/api/v1/task/activity/{taskId}` (v1, единственное число
  — это фикс сегодняшнего аудита, до него использовался неверный путь). Если
  для задачи лога нет — деградирует до «мини-истории» из штампов
  created/modified/completed прямо с самой задачи. 🟢.
- **get_changes** — агрегированная лента изменений по всему аккаунту за
  диапазон дат (создано/завершено/удалено/изменено), день-гранулярность в UTC
  (requires v2). 🟢.
- **get_project_members** — ⚠️ **чувствительный read (§2.2)** — выносит
  данные ДРУГИХ людей (имена/username, userId, роль владельца) за пределы
  личного контура Максима, а не только его собственные. Участники общего
  проекта + их userId (для назначения исполнителя). 🟢.
- **get_tasks_by_assignee** — ⚠️ **чувствительный read (§2.2)** — выносит,
  какие задачи назначены конкретному ДРУГОМУ человеку (не только Максиму) в
  общих проектах. Задачи, назначенные конкретному человеку (только в общих
  проектах, только явное назначение через поле Assignee). 🟢.
- **list_project_columns** — kanban-колонки проекта с их id (для
  `column_id`). 🟢.
- **operation_report** — см. отдельный разбор в разделе про создание/удаление
  ниже: независимый пост-факт отчёт по journal-записи. 🟢 read-only, но это
  и есть тот самый механизм независимой проверки для ВСЕХ пишущих методов.

## 2. Создание задач (plan → execute)

Официальный «правильный» путь для интерактивного чата — двухфазный:
`plan_task_creation` (read-only, строит манифест и ПРЕДЛАГАЕТ, но ничего не
создаёт) → пользователь отвечает текстом → `execute_task_creation(manifest_id,
user_reply=...)`. Прямой `create_tasks` для интерактивных ассистентов
ЗАБЛОКИРОВАН начисто — без `automation_key` (секрет, известный только
headless-автоматике/боту, НЕ модели в чате) он всегда возвращает отказ. Но
важная честная деталь: `execute_task_creation` вызывает `_require_consent`
с **tier=0** — а `_require_consent` при `tier<=0` возвращает `True` СРАЗУ,
не глядя вообще на `user_reply`. То есть создание объявлено «низкий риск,
обратимо» и реального серверного гейта на нём НЕТ — это 🟡, а не 🔴, несмотря
на то что докстрайнинг говорит «ОБЯЗАТЕЛЬНО user_reply».

- **create_tasks** — 🔴 для интерактивных вызовов (жёсткий отказ без
  `automation_key`), 🟢 для headless-автоматики с ключом. Поддерживает
  вложенные подзадачи до 4 уровней, теги, исполнителя, kanban-колонку,
  правило повтора, напоминания. **post-verify**: да — после создания
  перечитывает свежее состояние и сверяет, что каждая созданная задача
  реально легла в запрошенный проект/колонку (а не «куда-то ещё»), плюс
  проверяет, что подзадачи реально существуют. **journal**: да, `create`,
  можно `operation_report`.
- **plan_task_creation** — 🟢 read-only, строит манифест. Если project_id не
  передан — сервер САМ предлагает через LLM-подсказчик (`_suggest_destinations`),
  куда положить задачу, помечая «уверен»/«❓ не уверен» — никогда не выбирает
  «Тест» по умолчанию. Также подсвечивает дубликаты названий, уже открытые в
  целевом проекте.
- **execute_task_creation** — 🟡 (формально требует `user_reply`, но
  `_require_consent(tier=0)` пропускает независимо от его содержимого —
  создание считается низкорисковым/обратимым). Выполняет ровно то, что было в
  манифесте, добавляет `operation_report` в конец ответа автоматически (не
  нужно вызывать отдельно). **post-verify**: да (через тот же движок, что и
  `create_tasks`). **journal**: да.

## 3. Изменение задач (update / complete / move / parent / tags)

Общий паттерн этой группы: НИ ОДИН из этих методов НЕ вызывает
`_require_consent` — гейта в коде НЕТ вообще, только текст в докстринге
(«PROTOCOL: перед вызовом скажи пользователю и получи да»). Зато у всех есть
две реальные серверные защиты: (1) **identity-guard** — id сверяется с живым
названием/проектом ПЕРЕД мутацией, несовпадение = отказ; (2) **post-verify**
inline — сразу после мутации сервер перечитывает свежее состояние и печатает
«✅ проверено» либо «❌ не применилось», плюс journal-запись с `record_id` для
последующего `operation_report`.

- **update_tasks** — 🟡. Меняет title/content/даты/приоритет/теги/
  колонку/reminders/repeat/исполнителя, батчем или по одной (продвинутые поля
  — только по одной задаче за раз через официальный API). **Важный фикс
  сегодняшнего аудита**: `_sync_point_date` — если задача была «точечной»
  датой (`startDate == dueDate`) и передано только ОДНО из полей
  `start_date`/`due_date`, сервер синхронизирует второе поле на то же
  значение, чтобы задача не превратилась в незапланированный ДИАПАЗОН дат
  (раньше застревало на старой дате и рендерилось как «с 23-го по …»). Если
  задача УЖЕ была диапазоном — трогает только запрошенный край и добавляет
  предупреждение. **post-verify**: да, построчно сравнивает запрошенные
  изменения с живыми полями. **journal**: да, `update`.
- **complete_tasks** — 🟡. Батч через v2 (если >1 задачи) либо по одной через
  официальный API. **post-verify**: да — задача должна ИСЧЕЗНУТЬ из пула
  открытых после завершения, иначе «❌ complete НЕ сработал». **journal**: да,
  `complete`.
- **move_tasks** — 🟡. Перенос в другой проект/список. Гвардит и цель
  (`_guard_project`, fail-closed если id не резолвится), и сами задачи.
  **post-verify**: да — сверяет, что `projectId` в живом состоянии стал
  именно целевым. **journal**: да, `move`.
- **set_task_parent** — 🟡. Вложение одной или нескольких задач под родителя;
  дополнительно защищает от ЦИКЛА (нельзя вложить задачу под саму себя или
  своего потомка — строится цепочка предков) и от кросс-проектного вложения
  (все дети и родитель должны быть в одном проекте). **post-verify**: да,
  сверяет `parentId`. **journal**: да, `parent`.
- **unset_task_parent** — 🟢 (даже протокольного текста про подтверждение
  нет). Отцепляет подзадачу от родителя. Guard: сверяет, что текущий
  `parentId` РЕАЛЬНО равен переданному `parent_task_id`, иначе отказ.
  **post-verify**: да, `parentId` должен пропасть. **journal**: да, `parent`
  с `expect: {parentId: None}`.
- **set_task_tags** — 🟡. Заменяет полный набор тегов на задаче (не
  добавляет, а перезаписывает). Нормализует теги в нижний регистр без `#`.
  **post-verify**: да, сверяет итоговый набор тегов. **journal**: да, `tags`.
- **checkin_habit** — 🟢. Отмечает привычку (done/failed/not done),
  опционально задним числом. Identity-guard: id привычки должен резолвиться
  именно к переданному имени. Есть защита от ДВОЙНОГО чек-ина на одну дату
  (сверяет существующие отметки перед записью — иначе значение бы удвоилось).
  **post-verify**: НЕТ — после записи сервер просто возвращает то, что
  отправил, не перечитывая привычку заново. **journal**: нет,
  `operation_report` недоступен.

## 4. Удаление задач (полностью гейтовано — plan → «да» → execute)

Это единственная область, где гейт РЕАЛЬНО работает в коде (🔴), причём
даже для ОДНОЙ задачи. Механизм `_require_consent` (см. код вокруг строки
2277): проверяет, что манифест не «одноразовый уже использованный», не
протух (>1 часа), объекты не изменились между планом и подтверждением
(`_manifest_object_hash`), `user_reply` — это НАСТОЯЩЕЕ человеческое «да»
(словарь `_CONSENT_AFFIRMATIVE_WORDS`, не эхо служебного жаргона типа
`manifest_id`/`execute_...(`), и что между показом плана и подтверждением
прошло хотя бы `MIN_CONSENT_GAP` (по умолчанию 2 сек) — защита от того, что
модель сама вызовет plan и execute подряд в одном ходе, выдав это за
согласие пользователя.

- **delete_tasks** — 🔴. Для ОДНОЙ задачи (`DIRECT_DELETE_CAP=1`) допускает
  прямой вызов без явного `plan_task_deletion`, но всё равно строит
  одноразовый манифест внутри себя и требует `user_reply` вторым вызовом.
  Для batch (>1) — жёсткий отказ, обязателен `plan_task_deletion` →
  `execute_task_deletion`. Identity-guard обязателен (title каждой задачи
  должен быть передан). **post-verify + journal**: да, снимок задачи
  (`snapshot`) пишется в журнал ДО удаления (для восстановления вручную),
  после — сверка, что задача реально пропала из открытых.
- **plan_task_deletion** — 🟢 read-only, строит манифест. `with_subtasks=true`
  рекурсивно (BFS, любая глубина) разворачивает ВСЁ поддерево — без этого
  удаление родителя осиротило бы детей.
- **execute_task_deletion** — 🔴 полный гейт. Перед фактическим удалением
  ЕЩЁ РАЗ проверяет каждую позицию манифеста против живого состояния (title
  и project совпадают с тем, что видел человек при одобрении) — если задача
  успела измениться между планом и подтверждением, она пропускается
  («⏭ Пропущены — не совпали с одобренным планом»), а не удаляется вслепую.
  **post-verify + journal**: полные, плюс автоматически прикладывает
  `operation_report` в конец ответа.
- **delete_task_with_subtasks** — устаревший метод, который теперь ВСЕГДА
  отказывает и перенаправляет на `plan_task_deletion(with_subtasks=true)`.
  Ничего не удаляет ни при каких аргументах (бывший обходной путь
  `ALLOW_DIRECT_SUBTREE_DELETE` убран целиком).
- **delete_project** — 🔴 полный гейт (`action="delete_project"`,
  `tier=2`). Первый вызов без `user_reply` — только читает и показывает
  количество задач в проекте + сэмпл названий (до 20), ничего не удаляет.
  identity-guard fail-closed (`require_known=True` — если id вообще не
  резолвится к живому проекту, отказ БЕЗ права на сомнение). Каждый вызов
  перечитывает содержимое проекта ЗАНОВО (не кеширует между первым и вторым
  вызовом), так что дрейф контента естественно триггерит новый превью.
  **post-verify + journal**: да — снимок проекта и КАЖДОЙ задачи внутри
  пишется в журнал до удаления (каскадное удаление задач TickTick делает
  сам), после — проверка, что project_id больше не резолвится.

## 5. Разбор помойки / declutter (plan → «да» → execute, с опцией durable-таблицы)

Ретроактивный разбор ВСЕХ открытых задач: ищет точные и похожие дубликаты
(похожие — только если настроен `CLAUDE_CLI_URL`-шим-судья, иначе только
точные совпадения по названию), протухшие задачи (флаг, никогда не трогает
сам), группируемые «зонтичные» задачи, и предлагает SMART-переформулировки
расплывчатых названий. Ничего не мутирует до явного execute. Внутри execute
каждое действие идёт через УЖЕ аудированные инструменты (движок удаления,
`update_tasks`, `set_task_parent`) — то есть у каждой отдельной правки СВОЙ
identity-guard и пост-проверка, а `execute_declutter` просто агрегирует их
отчёты.

- **plan_declutter** — 🟢 read-only. Жёсткий кап на размер (по умолчанию 200
  открытых задач в области поиска, настраивается `max_tasks`) — иначе
  анализ O(n²) не успевает до таймаута MCP-клиента (~60с). `persist="sheet"`
  (опционально) сохраняет план в Google Sheet как durable источник истины —
  если таблица недоступна, план вообще НЕ строится (без тихого отката на
  RAM).
- **execute_declutter** — 🔴 полный гейт (`action="declutter"`, `tier=2`).
  Диспетчерит либо в RAM-манифест, либо (если план был сохранён с
  `persist="sheet"`) в отдельный sheet-движок. **post-verify + journal**:
  да, косвенно — через журналы под-операций (delete/update/set_task_parent),
  плюс сводный `operation_report` по всем задействованным record_id.
- **resume_declutter** — 🔴 полный гейт, но БЕЗ ссылки на исходный
  `plan_shown_at` (RAM-манифест мог погибнуть при рестарте Railway) —
  временная привязка `MIN_CONSENT_GAP` не проверяется, только сама
  подлинность `user_reply`. Только для sheet-режима. Безопасно вызывать
  повторно: строка со статусом `done` никогда не применяется дважды;
  зависший статус `applying` (после сбоя) сначала сверяется с ЖИВЫМ
  состоянием TickTick, а не берётся на веру.
- **set_declutter_decision** — 🔴 гейт, но ТОЛЬКО когда `decision="approved"`
  (`action="rename_tag_merge"`... нет, тут `action="declutter_decision"`).
  `decision="rejected"` — безопасно, гейта нет (это просто «не трогай»).
  Важное предупреждение из докстринга: `approved` — это НЕ безобидная
  пометка, а фактическое разрешение на удаление/переименование/группировку
  при следующем execute/resume. Пишет только колонку `decision` в таблицу,
  саму TickTick не трогает.

## 6. Проекты и группы проектов

- **create_project** — 🟢, без гейта, официальный API. **post-verify**: нет
  (просто возвращает объект, который прислал TickTick).
- **update_project** — 🟢, без гейта. Identity-guard fail-closed
  (`require_known=True`). **post-verify**: нет отдельной сверки после
  записи — возвращает объект от TickTick как есть (частично полагается на
  ответ API, а не на независимое перечитывание).
- **archive_project** — 🟢, без гейта. Разное поведение guard: при архивации
  (`archived=True`) fail-closed (`require_known=True`), при разархивации —
  мягкий (можно, даже если проект временно не резолвится по имени).
  **post-verify**: нет отдельной проверки после вызова.
- **create_project_group** — 🟢. **post-verify**: да — принудительно
  перечитывает свежий список групп и проверяет, что новая группа там есть.
- **delete_project_group** — 🟢 (протокольного текста про подтверждение
  тоже НЕТ, хотя удаление). Identity-guard обязателен по имени. Проекты
  внутри группы НЕ удаляются, просто теряют папку. **post-verify**: да,
  группа должна пропасть из свежего списка.
- **move_project_to_group** — 🟢. Guard и на проект, и на группу назначения
  (`group_id="NONE"` для разгруппировки). **post-verify**: да, сверяет
  живой `groupId` проекта после операции.
- **create_project_column** — 🟢. Kanban-раздел (requires v2). Identity-guard
  fail-closed на проект. **post-verify**: нет (возвращает id, который
  вернул TickTick, без повторного чтения).

## 7. Подзадачи, дублирование, won't-do

- **create_subtask** — 🟢. Guard на РОДИТЕЛЯ (title должен совпасть с живым),
  подзадача создаётся в реальном (не переданном) проекте родителя.
  **post-verify + journal**: да, `parent`, сверяет что создание видно и
  `parentId` реально указывает на родителя.
- **abandon_task** — 🟢. Помечает «не буду делать» (won't do). Guard
  обязателен. **post-verify + journal**: да, `abandon`, задача должна
  пропасть из открытых.
- **duplicate_task** — 🟢. Дублирует задачу в том же проекте. Явно
  предупреждает: НЕ переносятся чеклист (items), kanban-раздел и привязка к
  родителю — только базовые поля. **post-verify + journal**: да, `create`,
  проверяет что копия реально существует среди открытых.

## 8. Теги (создание/переименование/удаление)

- **create_tag** — 🟢, без гейта, без пост-проверки (просто фиксирует ответ
  TickTick).
- **rename_tag** — 🟢 в обычном случае (новое имя свободно). НО если
  `new_name` УЖЕ существует как тег — TickTick СЛИВАЕТ два тега
  (необратимо, теряется информация «какая задача носила какой тег») — тогда
  это 🔴: без `allow_merge=True` **И** `user_reply` (реального согласия через
  `_require_consent(action="rename_tag_merge", tier=2)`) метод откажет.
  Выставить `allow_merge=True` «на своё усмотрение» без `user_reply` НЕ
  считается достаточным — явно написано в докстринге. **post-verify**: да,
  старое имя должно исчезнуть, новое — появиться в свежем списке тегов.
- **delete_tag** — 🟢, без гейта, но показывает «blast radius» (сколько
  открытых задач лишится тега) в тексте ответа. **post-verify**: да, тег
  должен пропасть из свежего списка. Задачи не трогаются, только сам тег.

## 9. Комментарии к задачам

Общий паттерн: все три write-метода без гейта согласия (🟢), с
identity-guard на задачу и inline пост-проверкой (перечитывают список
комментариев и сверяют текст/наличие/отсутствие), без journal/
operation_report.

- **add_task_comment** — 🟢. Guard на задачу; если задача не среди открытых
  (например, завершена) — комментарий всё равно добавляется, но с явной
  припиской «название НЕ проверено».
- **update_task_comment** — 🟢. Сверяет, что новый текст РЕАЛЬНО виден в
  списке комментариев после правки.
- **delete_task_comment** — 🟢. Есть пред-проверка существования
  `comment_id` (отказ вместо тихого no-op на несуществующий id), после —
  сверка что комментарий пропал.

## 10. Вложения (включая вчерашние relay-ссылки download/upload)

Общий механизм: большие файлы не должны идти телом ответа MCP — поэтому
`/dl/{token}` и `/ul/{token}` — это отдельные HTTP-эндпоинты НА этом же
сервере (не на TickTick), подписанные HMAC-ключом, производным от
`MCP_SECRET` (не самим секретом — утёкшая ссылка не даёт доступа к MCP-
эндпоинту). Ссылки полностью STATELESS (всё нужное зашито в подписанный
токен, ничего не хранится на диске) и живут ограниченное время (по умолчанию
15 мин, максимум 120). Кука сессии TickTick никогда не покидает сервер —
только он делает запрос к TickTick и стримит байты клиенту.

- **attach_file_to_task** — 🟢, без гейта. Файл по URL (сервер качает сам)
  или base64. Максимум 20 МБ. Identity-guard на задачу. **post-verify**: да
  — сравнивает количество вложений ДО и ПОСЛЕ (не может проверить по имени
  конкретно, только по счётчику).
- **list_task_attachments** — см. раздел 1 (read-only).
- **download_task_attachment** — НЕ помечен как `READONLY` в коде (хотя по
  сути ничего не пишет в TickTick — только скачивает и кодирует в base64).
  Возвращает файл как base64 прямо в ответе, отказывает если файл больше
  15 МБ (лимит раздутия base64 в ответе). Для больших файлов докстринг явно
  отправляет к `get_attachment_download_url`.
- **get_attachment_download_url** — 🟢 read-only (аннотирован READONLY,
  хотя формально «создаёт» подписанную ссылку — сама ссылка не мутирует
  TickTick). Требует, чтобы сервер знал свой публичный адрес
  (`PUBLIC_BASE_URL`/Railway `RAILWAY_PUBLIC_DOMAIN`) и `MCP_SECRET`; без
  них — явный отказ с объяснением, а не тихая деградация.
- **create_attachment_upload_url** — 🟢, без гейта. Честное ограничение,
  прямо написанное в докстринге: САМ Claude не может воспользоваться этой
  ссылкой (не умеет делать сырые PUT-запросы) — она для человека с
  телефона/браузера или скрипта (`curl -X PUT --upload-file`). Если файл уже
  есть у Claude в руках — правильный путь `attach_file_to_task`, а не эта
  ссылка. Проверка размера (`size_bytes`) — заранее, до реальной загрузки.

## 13. Независимая проверка (journal / operation_report)

- **operation_report** — 🟢 read-only, но это ключевой механизм честности
  всей системы. Принимает `record_id` (от любого пишущего метода) ИЛИ id
  манифеста удаления. Перечитывает журнал `deletion_journal.jsonl` (что
  РЕАЛЬНО было запрошено на момент исполнения) и сверяет с ТЕКУЩИМ живым
  состоянием TickTick — для create проверяет проект/колонку, для update —
  каждое изменённое поле, для delete/complete/abandon — что объект пропал
  из открытых, для move — целевой проект, для tags/parent — итоговое
  значение. Явно инструктирует модель «перепечатай отчёт пользователю
  ДОСЛОВНО, не заменяй пересказом» — то есть даже финальный текст рассчитан
  на то, что модель не подменит вердикт сервера своим оптимизмом.
  **Важное честное ограничение**: `operation_report` работает ТОЛЬКО для
  методов, которые реально вызвали `_op_journal`/`_journal_write` —
  create/update/complete/delete/move/tags/parent/abandon/restore/
  delete_project/declutter. Методы без journal (теги create/rename/delete,
  комментарии, вложения, группы проектов, kanban-колонки, привычки,
  update_project/archive_project) полагаются ТОЛЬКО на inline-проверку в
  своём собственном ответе — отдельно перепроверить их позже нечем.

## 14. Разное (builder-хелперы — без обращения к API)

- **build_recurrence_rule** — 🟢, чистая функция, строит RRULE-строку

## Сводка по гейтам (честный подсчёт по коду, не по докстрингам)

- 🔴 Реальный серверный гейт (`_require_consent` с tier ≥ 1, реально блокирует
  без настоящего `user_reply`): **delete_tasks, execute_task_deletion,
  delete_project, execute_declutter, resume_declutter,
  set_declutter_decision (только decision="approved"), rename_tag (только
  ветка слияния), create_tasks (отказ без automation_key — другой механизм,
  но тоже жёсткий)** — итого 8 методов/веток с реальной остановкой.
- 🟡 Только протокольный текст в докстринге, гейта в коде нет:
  **execute_task_creation (tier=0, всегда проходит), update_tasks,
  complete_tasks, move_tasks, set_task_parent, set_task_tags,
  restore_tasks** — 7 методов.
- 🟢 Без подтверждения вовсе (либо read-only, либо признано
  дешёвым/обратимым): все остальные — **63 метода** (включая все read-only
  из разделов 1 и часть write-методов вроде create_project, create_tag,
  checkin_habit, комментарии, вложения, группы проектов, kanban-колонки).
