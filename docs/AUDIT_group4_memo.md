# Ревизия §16 — группа 4 (read-методы)

Дата: 2026-07-29. Файл: `ticktick_mcp/src/server.py`. Прогнан чек-лист §16
СТАНДАРТА (`~/.claude/skills/mcp-development-standard/STANDARD.md`) для
read-методов: `get_completed_tasks`, `list_tags`, `get_tasks_by_tag`,
`get_inbox_tasks`, `list_filters`. Гейт/identity-guard/post-verify/manifest
(п.2-7 чек-листа) к read-методам не применяются — это write-специфика.

Применимые пункты для read: §2.1 (аннотация read/write), §2.2
(секреты/чувствительность за пределами личного контура), §10.1
(капы/пагинация, честное усечение), §10.2 (таймауты/retry/429), §7.4 (язык
вывода), п.9 чек-листа (докстринг не должен обещать поведение, которого код
не гарантирует).

### 1. `get_completed_tasks` (server.py:5255-5274)

- §2.1: ✅ `@mcp.tool(annotations=READONLY)`.
- §2.2: ✅ без секретов, свой контур (личные завершённые задачи Максима).
- §10.1 капы: ⚠️ **молчаливое усечение.** Клиент-обёртка
  (`ticktick_v2_client.py:252-261`) жёстко клампит `limit` до
  `COMPLETED_MAX_LIMIT = 100` (`ticktick_v2_client.py:44,256):
  `limit = max(1, min(limit, COMPLETED_MAX_LIMIT))`. Если реально завершённых
  задач за период больше, чем запрошенный (клампнутый) `limit`, инструмент
  никак не сообщает об этом — `format_task_list(tasks)` в
  `server.py:5271` вызывается с собственным дефолтным лимитом форматирования
  100, который не срабатывает, так как `tasks` уже пришёл ограниченным с
  сервера API. В результате пользователь получает ровно `limit` записей без
  пометки «показано N из M» — прямое нарушение §10.1 («Молчаливое усечение
  НИКОГДА не допускается»).
- Докстринг (п.9 чек-листа): ⚠️ не упоминает жёсткий потолок в 100
  (`COMPLETED_MAX_LIMIT`). Докстринг обещает «Maximum number of completed
  tasks to return (default 50)», но если вызвать с `limit=500`, реально
  вернётся максимум 100 без предупреждения — докстринг вводит в заблуждение
  относительно фактического поведения.
- §10.2 таймауты/retry/429: ✅ идёт через общий `_request`
  (`ticktick_v2_client.py:167-179`) — `REQUEST_TIMEOUT`, retry с backoff на
  429/5xx.
- Обработка ошибок: ✅ единообразно с остальными v2-инструментами
  (`_ensure_ready()` → `try/except` → `logger.error` + текст ошибки).
- **Вердикт: ⚠️ есть замечания.** Молчаливое усечение при `limit`,
  превышающем `COMPLETED_MAX_LIMIT=100` (нарушение §10.1), и докстринг не
  документирует этот жёсткий потолок (нарушение принципа честного докстринга,
  п.9 чек-листа §16). Чинить: либо возвращать в тексте ответа пометку «показано
  100 из ограничения API» когда `len(tasks) == COMPLETED_MAX_LIMIT`, либо явно
  прописать потолок в докстринге.

### 2. `list_tags` (server.py:5277-5291)

- §2.1: ✅ READONLY.
- §2.2: ✅ без секретов, свой контур.
- §10.1 капы: без явного лимита/пагинации — `ticktick_v2.get_tags()`
  (`ticktick_v2_client.py:232-233`) отдаёт весь список тегов из
  `get_state()` целиком, `list_tags` в `server.py:5284-5288` рендерит все без
  среза. Формально это расхождение с буквой §10.1 («любой read-метод,
  способный вернуть много, ДОЛЖЕН иметь явный кап»), но по природе данных —
  теги личного аккаунта TickTick — практический потолок в реальности низкий
  (десятки, не тысячи), риск раздутия контекста модели минимален. Отмечаю как
  техническое несоответствие буквы стандарта, не как функциональный дефект.
- §10.2: ✅ таймауты/retry через `_request`.
- Докстринг: ✅ честный, минимальный, ничего лишнего не обещает.
- **Вердикт: ✅ соответствует** (с оговоркой о формальном отсутствии капа —
  низкий риск, см. выше).

### 5. `list_filters` (server.py:5641-5657)

- §2.1: ✅ READONLY.
- §2.2: ✅ без секретов — `rule` в фильтре это пользовательское условие
  выборки (TickTick smart list), не токен и не credential.
- §10.1 капы: без явного лимита, как и `list_tags` — `get_filters()`
  (`ticktick_v2_client.py:296-297`) отдаёт весь список из `get_state()`.
  Количество сохранённых умных списков у пользователя по природе мало
  (единицы-десятки), риск низкий; формальное несоответствие буквы §10.1, не
  функциональный дефект.
- §10.2: ✅ таймауты/retry есть.
- Докстринг: ✅ «List saved smart-list filters with their query rules»
  соответствует коду один в один.
- Мелкое наблюдение (не дефект): вывод показывает сырой `id` фильтра в теле
  (`server.py:5653`, `(id: {f.get('id')})`). §7.1 («объекты — названиями, не
  id») формально относится только к write-методам, а здесь `id` практически
  полезен (нужен для последующего использования фильтра), так что это не
  нарушение для read-инструмента.
- **Вердикт: ✅ соответствует.**

## Сквозной пункт §7.4 (язык вывода) — по всем пяти методам

⚠️ **Расхождение у всех пяти**, как и во всех ранее проверенных группах
(group1-3): весь видимый Максиму текст — на английском («Completed tasks
(N):», «No tags found.», «Tags (N):», «No open tasks in the Inbox.», «Error
fetching filters: ...»). §7.4 требует русский «без исключений» для текста,
видимого Максиму. Не считаю это новым/уникальным дефектом группы 4 — это уже
зафиксированное сквозное расхождение по всему server.py (см.
`docs/AUDIT_group1_memo.md`), требующее отдельного решения Максима
(распространять ли §7.4 на read-методы или ограничить write-методами), а не
точечного патча пяти инструментов этой группы.
