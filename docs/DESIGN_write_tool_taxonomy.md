# Таксономия пишущих инструментов TickTick MCP + рекомендации по гейту

Проектный документ от 2026-07-27. **READ-ONLY проектирование** — код не менялся,
TickTick не трогался. Основа: аудит `docs/PIPELINE_ticktick_mcp.md` + сверка
докстрингов и тел функций в `ticktick_mcp/src/server.py`.

Задача этого файла — **классификация**, а не проектирование самого механизма
подтверждения. Столбец «Рекомендация гейта» говорит только КОМУ гейт нужен и
какой силы; КАК его реализовать (кнопка, отдельный канал, токен, тайм-аут) —
проектирует параллельный агент. Формат вывода инструментов здесь тоже не
проектируется.

---

## 0. Что считаем «пишущим инструментом»

Из 76 `@mcp.tool()` в `server.py` аннотацию `annotations=READONLY` НЕ несут
**35** функций — это и есть кандидаты в «пишущие». Из них:

- `plan_task_creation` / `plan_task_deletion` / `plan_declutter` — помечены
  READONLY, только строят манифест, живые данные не трогают → **в таблицу не
  входят**.
- `operation_report` — READONLY пост-проверка → не входит.
- `download_task_attachment` — пишет **на локальный диск**, а не в TickTick;
  это скачивание, безобидно и обратимо (удали файл). Включаю в таблицу отдельной
  строкой с пометкой, что это не мутация TickTick.

Итого в таблице ниже — **35 инструментов** (34 меняющих TickTick/состояние + 1
локальное скачивание). Это и есть «~34», о которых речь в задаче.

### Легенда

**Обратимость:**
- ✅ обратимо легко (одним обратным действием: uncomplete, unarchive, move назад)
- ⚠️ обратимо с потерей (перезапись поля/набора — старое значение теряется, нужен
  ручной ре-набор; или откат только вручную из журнала/корзины)
- ❌ необратимо (постоянное удаление; откат только вручную и не всегда возможен)

**Масштаб:**
- ОДНА — одна задача/объект за вызов
- ПАКЕТ — несколько задач за вызов (batch-список)
- ПРОЕКТ/МАССА — целый проект, все задачи с тегом, вся структура

**Рекомендация гейта:**
- 🔴 **НАСТОЯЩИЙ ГЕЙТ** — нужен реальный код-барьер (необратимо × большой радиус)
- 🟡 **ЛЁГКОЕ подтверждение** — обратимо, но с потерей/заметным эффектом; хватит
  явного «да» + честного эха, полноценный крипто-гейт избыточен
- 🟢 **БЕЗ гейта** — мелкое, обратимое, легко откатывается; барьер только мешает

Принцип: **сила гейта ∝ (необратимость × радиус поражения)**. Обратимое создание
и правки — не гейтить; необратимые удаления и массовые/проектные операции —
настоящий гейт.

## 2. Врущие / вводящие в заблуждение докстринги

Найдено **3 явных** случая (аудит указал 2 — третий добавлен) + 1 системная
формулировка-приукрашивание. Для каждого — точный исправленный текст.

### 2.1. `plan_task_deletion` (:1889-1891) — ФАКТИЧЕСКИ ЛОЖЬ

**Сейчас:**
> `Phase 1 of SAFE deletion — THE way to delete tasks (direct delete_tasks is disabled): build a deletion MANIFEST without deleting anything.`

**Почему ложь:** `delete_tasks` (:1734-1739) прямое удаление НЕ отключено — оно
разрешено для ≤`DIRECT_DELETE_CAP` (default 1) задач. Читающий только этот
докстринг не узнает про открытую прямую дверь.

**Исправленный текст:**
> `Phase 1 of SAFE deletion — the two-phase (plan → confirm → execute) path, REQUIRED for bulk deletes and for parent+subtree deletes. (A single task MAY still be removed directly via delete_tasks when its title is supplied, up to DIRECT_DELETE_CAP=1; anything larger is refused there and routed here.) Builds a deletion MANIFEST without deleting anything. Read-only — safe to call without confirmation.`

### 2.2. `delete_task_with_subtasks` (:3678-3695) — ОПИСЫВАЕТ НЕСУЩЕСТВУЮЩЕЕ ПОВЕДЕНИЕ

**Сейчас** докстринг детально описывает активное удаление:
> `⚠️ Delete a parent task AND all its subtasks in one go. Finds every subtask whose parentId matches task_id, deletes them via batch delete, then deletes the parent itself.` (+ инструкции про `summary` с ⚠️ для «confirmation dialog»)

**Почему ложь:** тело функции (:3703-3707) **всегда** возвращает отказ и
редиректит на `plan_task_deletion`. Инструмент НИКОГДА ничего не удаляет.
Докстринг обещает удаление и параметры (`summary`, `project_name`), которые ни на
что не влияют. Модель может выбрать этот инструмент, ожидая результата, и
получить только отказ; хуже — поверить, что «удаление поддерева здесь и
происходит».

**Исправленный текст:**
> `DEPRECATED / always refuses. Subtree deletion is NOT performed here — this tool exists only to catch old callers and redirect them. It always returns a refusal pointing to plan_task_deletion with {"taskId","title","with_subtasks":true}, which expands the ENTIRE open subtree into a manifest for approval. No arguments have any effect; nothing is ever deleted by this tool.`

(Аргументы стоит оставить в сигнатуре для обратной совместимости, но докстринг
не должен делать вид, что они работают.)

### 2.3. `set_declutter_decision` (:3620-3630) — ВВОДИТ В ЗАБЛУЖДЕНИЕ О СВОЙСТВЕ БЕЗОПАСНОСТИ

**Сейчас:**
> `…the deterministic chat-approval path…: instead of the human editing the Google Sheet by hand, Claude proposes/relays a decision here and the CODE writes it…`

**Почему вводит в заблуждение:** формулировки «chat-approval path» и «Claude
proposes/relays a decision» подают запись как *передачу человеческого одобрения*.
На деле код НЕ проверяет, что человек одобрил — он пишет `approved` по одному
слову модели. Название «approval» создаёт ложное ощущение согласованности; именно
через это поле `execute_declutter`/`resume_declutter` затем «слепо» удаляют.

**Исправленный текст:**
> `Writes the `decision` column (approved/rejected) for specific rows of a sheet-backed declutter manifest. WARNING: this tool performs NO check that a human actually approved — it writes whatever `decision` the caller passes. Downstream execute_declutter/resume_declutter treat `approved` rows as ready to delete/modify, so writing `approved` here is equivalent to authorizing those changes. Only pass decision="approved" after the user has explicitly approved the exact rows; passing it without genuine human confirmation silently arms a destructive run.`

### 2.4. Системная формулировка «confirmation dialog» (~15 инструментов) — ПРИУКРАШИВАНИЕ

`delete_tasks`, `delete_project`, `delete_task_with_subtasks`, `restore_tasks`,
`abandon_task`, `duplicate_task`, `move_tasks`, `set_task_parent`,
`create_subtask` и др. описывают `summary` как строку, «shown at the TOP of the
**confirmation dialog**». **Никакого диалога код не показывает и не ждёт** —
`summary` это просто текст, который модель ДОЛЖНА вывести пользователю. Фраза
создаёт впечатление UI-барьера, которого нет.

**Рекомендация:** заменить «confirmation dialog» на честное «the one-line summary
you MUST show the user before proceeding (there is no server-side dialog; showing
it and getting a real ‘yes’ is the model's responsibility)». Это не отдельный
баг-докстринг, а сквозная правка формулировки во всех перечисленных.

## 3. Заметки на будущее (не гейт, но связано)

- **Три пути создания задач** с разной строгостью: `create_tasks` (HMAC) /
  `create_subtask` (без текста) / `duplicate_task`. Все обратимы → все 🟢, но
  формат/журнал стоит унифицировать, чтобы модель не «проваливалась» в самый
  тихий путь.
- **`rename_tag` `allow_merge`** — единственный, помимо крипто-гейта
  `create_tasks`, реальный код-гейт на необратимую ветку. Хороший референс:
  «опасная ветка блокируется флагом, который сервер требует явно».
- **`delete_tag`** уже считает `carriers` (число носителей) — готовая метрика,
  чтобы завязать силу гейта на радиус (0-2 носителя → 🟡, много → 🔴).
