Дата: 2026-07-29. Файл: `ticktick_mcp/src/server.py` (+ `ticktick_v2_client.py`
для `get_task_activity`). Прогнан чек-лист §16 для read-методов:
`list_task_attachments`, `search_all_tasks`, `get_task_info`, `get_task_activity`,
`get_changes`. Гейт/identity-guard/post-verify (п.2-7 чек-листа) не применяются —
это write-специфика. `get_task_activity` вчера чинили (коммит `f87c6f0`,
2026-07-27) — логика НЕ трогалась, только сверка докстринга с кодом.

Применимые пункты: §2.1 (аннотация), §2.2 (секреты/чувствительность), §10.1
(капы/пагинация), §7.4 (язык), честность докстринга.

### 2. `search_all_tasks` (server.py:7251-7408)
- §2.1: ✅ READONLY.
- §2.2: ✅ без секретов.
- §10.1 капы: ⚠️ **неполный.** Путь `open_matches` — честно: `format_task_tree(
  open_matches, 100)` даёт явное «...and N more» при усечении (server.py:7384,
  ссылается на 856-857). А вот `closed_matches` (7389) и `comment_matches`
  (7401) режутся тем же способом — `[:100]` без truncation-сообщения, если
  реальных совпадений больше 100. Молчаливое усечение прямо запрещено §10.1
  («модель сделает вывод по неполным данным»); формально это тот же паттерн
  пробела, что нашёлся в группе 1 у `get_project_tasks`.
- Докстринг: ✅ честный и подробный (объясняет scope/match/fields/comment cap
  на 150 фетчей — этот cap как раз честно репортится через `comment_capped`).
- **Что чинить:** добавить «...and N more» / «показано 100 из M» к
  `closed_matches` и `comment_matches`, аналогично `open_matches`.
- **Вердикт: ⚠️ частичный пробел (§10.1)** — cap для open честный, для
  closed/comment — молчаливый.

- **Вердикт: ✅ соответствует.**

### 4. `get_task_activity` (server.py:7542-7623, клиент: ticktick_v2_client.py:461-534)
- §2.1: ✅ READONLY.
- §2.2: ✅ без секретов; `whoProfile.displayName` для не-владельца — имя
  коллаборатора шаренного списка, уже доступное этому аккаунту через API
  (не «чужой контур» в смысле §2.2 — тот же прецедент, что в группе 1 для
  участников шаренных проектов).
- §10.1 капы: ⚠️ **теоретический пробел.** Клиент честно пагинирует до
  `max_pages=20` (ticktick_v2_client.py:463,524), но если у задачи реально
  больше 20 страниц активности, обрезка происходит **молча** — ни докстринг
  инструмента, ни тело ответа не говорят «показаны не все события». На
  практике маловероятно (20 страниц активности на одну задачу — экстремальный
  край), но формально расходится с «молчаливое усечение никогда не
  допускается».
- **Докстринг vs код — сверка честности (это была основная цель прогона):**
  ✅ **докстринг полностью соответствует коду.** Проверено построчно:
  - «Backed by ... `GET /api/v1/task/activity/{taskId}` (v1, singular
    "activity", no projectId in the path)» — совпадает с
    `ATTACHMENT_BASE}/task/activity/{task_id}` (ticktick_v2_client.py:482).
  - «Automatically walks all pages» — совпадает с циклом `for _ in
    range(max(1, max_pages))` (client.py:524-533), НО докстринг не упоминает
    сам `max_pages=20` предел — см. пробел выше, это неточность через
    умолчание, а не прямая ложь.
  - «If this specific task genuinely has no logged activity (empty result or
    404), falls back to the created/modified/completed stamps» — совпадает с
    `_task_activity_fallback` (server.py:7509-7539) и веткой `if not events` /
    веткой `except` при `"404" in str(e)` (server.py:7568-7573, 7618-7622).
  - `project_id` описан как «kept for backward compatibility; no longer
    needed» — совпадает: клиентский вызов `ticktick_v2.get_task_activity(
    project_id, task_id)` передаёт его позиционно, но URL его не использует
    (client.py:461-482 — `project_id` не входит в `url`).
  - Никаких обещаний «диалог подтверждения» или несуществующей функциональности
    нет — п. §7.4/блокер-критерий не нарушен.
- **Вердикт по докстрингу: ✅ честен**, логика вчерашнего фикса не тронута.
  **Вердикт по §10.1: ⚠️ мелкий пробел** (недокументированный max_pages cap).

### 5. `get_changes` (server.py:7626-7713)
- §2.1: ✅ READONLY.
- §2.2: ✅ без секретов.
- §10.1 капы: ❌ **реальный пробел, хуже чем у `search_all_tasks`.**
  - `open_tasks = ticktick_v2.get_open_tasks()` — **без лимита вообще**
    (server.py:7668).
  - `completed` капается на 100 (7669-7670), `trash` — на 300 (7671), это
    честные капы на входе, но:
  - Финальный список `events` строится из всех трёх пулов и выводится
    **целиком**, без какого-либо капа на количество строк в самом ответе
    (server.py:7702-7710) — только заголовок с честным `len(events)`, но не
    «показано N из M» / без обрезки текста. Для активного аккаунта с широким
    диапазоном дат (`since`/`until`) это неограниченный по размеру ответ —
    тот же паттерн, что `get_project_tasks` в группе 1 (там это было
    признано ❌, не ⚠️, именно из-за отсутствия капа на сам вывод, а не
    только на источник данных).
- Докстринг: ✅ честный, корректно описывает day-granularity/UTC-нюанс дат.
- **Что чинить:** добавить cap на `events` (например 200) с truncation-note,
  и/или явный cap на `get_open_tasks()` для больших аккаунтов.
- **Вердикт: ❌ реальный пробел (§10.1)** — самый широкий по потенциальному
  объёму ответа метод в этой группе.

## Сквозной пункт §7.4 (язык вывода)

⚠️ **Расхождение внутри самой группы, не только с группой 1.** 4 из 5 методов —
на английском (`list_task_attachments`, `search_all_tasks`, `get_task_info`,
`get_task_activity`), а **`get_changes` уже полностью на русском**
(«Изменения с {since} по {until}», «Создано:», «Изменено:», «Завершено:»,
«Удалено (в корзине):», server.py:7684-7709). Это тот же открытый вопрос, что
в группе 1: либо §7.4 явно ограничивается write-методами (тогда 4 read-метода
не баг), либо все read переводятся на русский вслед за `get_changes` —
нужно решение Максима, не самостоятельная правка.
