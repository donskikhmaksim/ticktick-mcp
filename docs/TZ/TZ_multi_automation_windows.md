# ТЗ-аддендум: несколько одновременных временных окон (не одно)

**Статус:** уточнение владельца 2026-08-11, поверх `docs/TZ/TZ_temp_automation_key.md`.

## Зачем

Владелец объяснил дословно (2026-08-11): "Я просил по кнопке в боте
генерировать новый ключ, который будет работать 24 ч, я его буду
вставлять в чаты где мне нужна автоматика." — то есть он использует
временные ключи В НЕСКОЛЬКИХ РАЗНЫХ ЧАТАХ/СЕССИЯХ одновременно, и каждой
нужен свой.

Текущая реализация (`ticktick_mcp/src/automation_key.py`,
`generate_window`/`check_window`/`revoke_window`/`window_status`) хранит
**ровно одно** окно на сервер — `_WINDOW_ID = SERVER` фиксирован, повторная
генерация делает `UPSERT` этой же строки и **инвалидирует предыдущий
токен**. Это ломает ровно тот сценарий, который просил владелец: сгенерировал
ключ для чата А → вставил его туда → сгенерировал ключ для чата Б → ключ
чата А молча перестал работать.

Статический канал `AUTOMATION_KEY` (env, для n8n/автоматизаций) этим
аддендумом НЕ затрагивается — он как раз один, постоянный, это уже
правильно и отдельно от временных окон.

## Что менять

### Таблица `tg_automation_windows`

Убрать одно-строчность. Новая схема (миграция — новая таблица или ALTER,
смотри по месту, но НЕ теряя уже созданные записи, если совместимость
позволяет):

```sql
CREATE TABLE IF NOT EXISTS tg_automation_windows (
    server          TEXT NOT NULL,
    window_id       TEXT PRIMARY KEY,   -- случайный короткий id на КАЖДУЮ генерацию,
                                         -- не фиксированный `server` как раньше
    token_hash      TEXT NOT NULL,
    label           TEXT,               -- необязательная метка ("чат с Х"), NULL по умолчанию
    created_at      BIGINT NOT NULL,
    expires_at      BIGINT NOT NULL,
    revoked_at      BIGINT,
    created_by_chat TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS tg_automation_windows_lookup_idx
    ON tg_automation_windows (server, revoked_at, expires_at);
```

### `automation_key.py` — новые/изменённые функции

- `generate_window(chat_id, label=None) -> str` — **INSERT**, не UPSERT.
  Новый случайный `window_id` (например `secrets.token_hex(6)`) на каждый
  вызов. Старые записи не трогает. Возвращает сырой токен один раз.
- `check_window(provided) -> bool` — теперь ищет совпадение СРЕДИ ВСЕХ
  активных (`revoked_at IS NULL AND expires_at > now`) строк для
  `server='ticktick'`, не одной фиксированной. При множестве активных окон
  — сравнение каждого хэша по очереди (все constant-time), первое
  совпадение засчитывается.
- `revoke_window(window_id, chat_id) -> bool` — теперь принимает КОНКРЕТНЫЙ
  `window_id` (не общий `server`-ключ). Гасит только его.
- `revoke_all_windows(chat_id) -> int` — новая функция, гасит все активные
  разом (возвращает число погашенных) — на случай "выключи всё".
- `list_windows(chat_id="") -> List[Dict]` — новая функция, все АКТИВНЫЕ
  окна (id, label, created_at, expires_at, remaining_s) — без хэшей и без
  сырых токенов (те не восстановимы принципиально).
- `window_status` (старая, на одно окно) — можно оставить как алиас
  "последнее" или убрать в пользу `list_windows`, смотри по месту,
  что естественнее для вызывающего кода в `tg_approval.py`.

### Команды в Telegram (`/automation_key`)

- `/automation_key` (без аргумента) или кнопка "Новый ключ" → генерирует ОЧЕРЕДНОЕ окно (не трогая существующие), присылает токен.
- `/automation_key list` / кнопка "Список" → показывает все активные окна (id, когда создано, сколько осталось) — без самих токенов, их не восстановить.
- `/automation_key revoke <id>` / кнопка на конкретной строке списка → гасит одно окно.
- `/automation_key off` / кнопка "Выключить всё" → гасит все разом
  (`revoke_all_windows`).

### Аудит в отчёте (уже частично сделано в `_automation_key_channel`)

Метка канала `"window:<created_at>"` уже несёт время создания — при
множественных окнах этого достаточно для различения В ОТЧЁТЕ, отдельно
проверить, что `_automation_key_channel` ищет совпадение среди ВСЕХ
активных окон (после правки `check_window`), а не только "первого".

## Тестовый план (дополнение)

1. Сгенерировать окно А, затем окно Б — оба валидны одновременно (окно А
   НЕ инвалидируется генерацией Б).
2. `revoke_window(id_А)` гасит только А — Б продолжает работать.
3. `revoke_all_windows` гасит оба разом.
4. `list_windows` показывает оба активных, не показывает погашенные/истёкшие.
5. Каждое окно истекает по СВОЕМУ собственному времени (А создано раньше —
   истекает раньше, Б продолжает работать).
6. Существующие тесты `tests/test_automation_key_windows.py` и
   `tests/test_automation_key_telegram.py` (14 пунктов из основного ТЗ) —
   адаптированы под новую сигнатуру, все зелёные, ни один регресс.

## Исчезновение сообщения с самим ключом — 10 секунд, не минута

Отдельное требование владельца (2026-08-11): сообщение, в котором бот
показывает СВЕЖЕСГЕНЕРИРОВАННЫЙ токен, должно самоудаляться через **10
секунд** после отправки — короче общего таймера гейта (минута, §5
основного ТЗ), потому что здесь в чате какое-то время лежит открытым текст
самого секрета, а не план/отчёт.

Механизм — тот же `schedule_message_delete` (`tg_approval.py`), которым уже
пользуется удаление сообщений гейта, только с явным `delay_s=10` вместо
дефолтных 60 (сигнатура уже это позволяет — параметр `delay_s` опционален,
менять её не нужно, просто передать другое значение в этом конкретном
месте вызова — там, где отправляется сообщение с токеном после
`generate_window`).

Тест: сообщение с токеном стоит в очереди на удаление через ~10с, а НЕ
через ~60с, как обычные сообщения гейта.

## Явно НЕ меняется

- Статический `AUTOMATION_KEY` (env) — один, постоянный, для n8n. Не
  трогаем.
- `MCP_SECRET` как временный legacy-канал — не трогаем.
- Исчезновение сообщений гейта (§5 основного ТЗ) — не трогаем.
