# ТЗ: automation_key — отдельный ключ для автоматики + временный по кнопке в Telegram

**Статус:** уточнено владельцем 2026-08-10, в реализации. Отдельная работа, не входит в перечень 18 пунктов "Заход 1" (`docs/TZ/ZAHOD1.md`).

## 1. Зачем

Сейчас `automation_key` сверяется с `MCP_SECRET`
(`ticktick_mcp/src/server.py:66`, `_automation_key_matches`, `:109-128`) — а
у `MCP_SECRET` уже есть ДВЕ ДРУГИЕ роли (путь `/mcp/<secret>` и корень ключа
подписи вложений, `.env.template`). Три обязанности на одном секрете —
ротация ради одной ломает остальные две.

Владелец явно попросил (2026-08-10) разделить на ТРИ независимых канала:

1. **`MCP_SECRET`** — как есть, для двух своих старых ролей (путь `/mcp/`,
   подпись вложений). Роль automation_key у него ЗАБИРАЕТСЯ.
2. **Новый статический `AUTOMATION_KEY`** — отдельный секрет, НЕ равный
   `MCP_SECRET`. Генерируется один раз, зашивается кодом во внешние
   автоматизации (n8n и подобные), меняется редко и осознанно.
3. **Временные ключи** — случайная строка (`secrets.token_urlsafe`),
   выдаётся по кнопке/команде в Telegram, окно 24 часа, хранится ХЭШЕМ в
   базе (раздел 3.1 ниже).

Владелец так же явно попросил (2026-08-10) минисервис — самостоятельный
модуль под управление жизненным циклом обоих новых каналов (генерация,
проверка, отзыв, статус), а не разбросанный по `server.py` код. Портируемый
byte-for-byte модуль (тот же приём, что уже есть у `tg_approval.py`,
`tg_auto_execute.py`) — на будущее его можно скопировать в другие MCP-репо
из этой же экосистемы (раздел 7 отмечает это отдельно, сейчас реализуется
только для ticktick-mcp).

## 2. Что НЕ меняется

- `MCP_SECRET` остаётся как есть для своих двух старых ролей (путь `/mcp/`,
  подпись вложений) — только роль automation_key у него забирается.
- **Обратная совместимость на переходный период**: пока `AUTOMATION_KEY` не
  создан и не роздан внешним автоматизациям, старый `MCP_SECRET` ПРОДОЛЖАЕТ
  приниматься как automation_key — иначе существующие n8n-сценарии сломаются
  молча в момент выкладки. Отдельным шагом (не в этом ТЗ) владелец переводит
  внешние автоматизации на новый ключ и потом может попросить убрать приём
  `MCP_SECRET` как automation_key явной отдельной правкой.
- Approval gate (план → подтверждение) для инструментов вне временного окна
  работает как сейчас.
- Весь механизм скрытия 13 прямых инструментов из листинга (1.3.4) не
  трогается — временный/новый статический ключ снимает ТОЛЬКО требование
  ключа/подтверждения, не возвращает инструменты в список модели.

## 3. Предлагаемый механизм

### 3.1. Хранилище

Новая таблица (по образцу `mcp_manifests`/`tg_approvals`,
`ticktick_mcp/src/manifest_store.py:182`, `ticktick_mcp/src/tg_approval.py:862`),
на том же `CONSENT_DATABASE_URL`:

```sql
CREATE TABLE IF NOT EXISTS tg_automation_windows (
    server          text NOT NULL,          -- 'ticktick', на будущее — общая таблица
    window_id       text PRIMARY KEY,
    token_hash      text NOT NULL,           -- sha256 токена, НЕ сам токен
    created_at      bigint NOT NULL,         -- unix ms
    expires_at      bigint NOT NULL,         -- created_at + 24ч (настраиваемо)
    revoked_at      bigint,                  -- NULL, пока не отозван вручную
    created_by_chat text NOT NULL
);
```

Хранить хэш, не сам токен — тот же принцип, что и у остальных секретов в
этом слое (см. `ticktick_mcp/src/tg_approval.py:1353`, комментарий про DSN с
паролем в открытом виде).

### 3.2. Генерация — команда/кнопка в Telegram

- Owner-only проверка — тот же паттерн, что уже используется для
  `callback_query.from.id` (`ticktick_mcp/src/tg_approval.py:1230`).
- Команда `/automation_key` → сообщение с инлайн-кнопками (Показать ключ /
  Выключить / Статус) — держит принцип "по кнопке" для самих действий.
- Нажатие "Показать ключ" → `secrets.token_urlsafe(32)` → хэш в базу,
  `expires_at = now + AUTOMATION_WINDOW_HOURS` → токен отправляется
  владельцу отдельным сообщением в чат. Чат уже доверенный owner-only канал
  (тот же принцип, на котором стоит вся кнопка подтверждения) — плейнтекст
  здесь не новый прецедент.
- Вебхук расширяется с `allowed_updates: ["callback_query"]` на
  `["callback_query", "message"]` (`register_webhook`, `tg_approval.py:1314`)
  — owner-only проверка на `message.from.id` та же, что уже стоит на
  `callback_query`.

### 3.3. Отзыв и статус

- Кнопка "Выключить окно сейчас" — `revoked_at = now`.
- Кнопка/команда "Статус" — активно ли окно, сколько осталось.

### 3.4. Проверка ключа — три уровня

`_automation_key_matches` расширяется до трёх независимых проверок подряд
(первая совпавшая побеждает, порядок значения не имеет — все три
constant-time):

1. Новый статический `AUTOMATION_KEY` (env, отдельно от `MCP_SECRET`).
2. Временный ключ — хэш присланного значения ищется в
   `tg_automation_windows` по `server='ticktick' AND revoked_at IS NULL AND
   expires_at > now()`.
3. Старый `MCP_SECRET` — **временно**, ради обратной совместимости (раздел
   2). Убирается отдельной правкой, когда владелец подтвердит, что все
   внешние автоматизации переведены на `AUTOMATION_KEY`.

Все три канала независимы: активность одного не влияет на остальные.

### 3.5. Минисервис — отдельный модуль

Новый файл `ticktick_mcp/src/automation_key.py` (портируемый byte-for-byte,
по образцу `tg_approval.py`) берёт на себя ВСЁ, что касается обоих новых
каналов (2 и 3 из раздела 1) в одном месте, а не размазывается по
`server.py`:

- `matches_static(provided) -> bool` — сравнение с `AUTOMATION_KEY`.
- `generate_window(chat_id) -> str` — создаёт запись в `tg_automation_windows`,
  возвращает сырой токен (кладётся в базу только хэш).
- `check_window(provided) -> bool` — ищет непросроченный, неотозванный хэш.
- `revoke_window(chat_id) -> bool` — гасит активное окно (`revoked_at = now`).
- `window_status(chat_id) -> Optional[dict]` — активно ли, сколько осталось.

`server.py` зовёт только эти функции — деталей схемы базы/генерации
токена в `server.py` не появляется, ровно как `manifest_store`/`tg_approval`
сегодня инкапсулируют свою часть.

### 3.6. Решения по открытым вопросам

(Решено самостоятельно, по стандартному режиму этой сессии — не переспрашивать, докладывать результатом.)

1. **Ограничение по типам операций** — НЕТ, окно/новый ключ снимают
   требование единообразно, без специальных исключений.
2. **Где живёт вход генерации** — команда `/automation_key`, см. 3.2.
3. **Срок 24 часа** — константа `AUTOMATION_WINDOW_HOURS` (env,
   default=24) в `automation_key.py`.
4. **Повторное нажатие при активном окне** — ПРОДЛЕВАЕТ (перезаписывает
   `expires_at = now + 24ч`, генерируется новый токен, старый хэш
   инвалидируется заменой строки).

## 4. Аудируемость — обязательное условие, не опция

Операция, исполненная под временным окном ИЛИ новым статическим ключом,
обязана быть **отмечена отдельно** в отчёте (`operation_report`/журнал) —
иначе теряется весь смысл прозрачности, вокруг которой построен весь
сегодняшний Заход 1 ("ни одна проверка не полагается на дисциплину
модели", `docs/TZ/ZAHOD1.md:16-29`). Разграничение в отчёте: "исполнено
автоматикой (`AUTOMATION_KEY`)" / "исполнено в открытом окне (временный
ключ, открыт `<когда>`)" / "исполнено автоматикой (`MCP_SECRET`, устаревший
путь)".

## 5. Исчезновение сообщений — не копить историю в чате

Отдельное требование владельца (2026-08-10): сообщения гейта, которые уже
"ушли в отчёт" (результат доступен через `operation_report`/журнал), должны
самоудаляться из чата примерно через 1 минуту после того, как их роль
исполнена — иначе чат бесконечно копит историю подтверждений.

**Что именно и когда удаляется** (таймер стартует от МОМЕНТА, когда
сообщение исполнило свою роль, а не от момента отправки — план может
провисеть в ожидании нажатия сколько угодно):

- Сообщение с планом/кнопками — таймер стартует, когда пришёл ответ
  (нажатие кнопки или разбор текстового "да"/отказа), не раньше.
- Сообщение-отчёт о результате — таймер стартует сразу при отправке (оно и
  так уже финальное).

**Механизм.** Небольшая табличка в памяти процесса достаточна (не нужна
долговечность через рестарт — потеря пары сообщений на "не удалилось
секунда в секунду" не критична, в отличие от манифестов): список
`(chat_id, message_id, delete_after_ts)`. Существующий периодический
поллер (`_tg_auto_execute_tick`, `tg_auto_execute.py`) на каждом проходе
дополнительно проверяет список и зовёт Telegram `deleteMessage` для всего,
что просрочено, убирая запись из списка. Ошибку удаления (сообщение уже
стёрто вручную, чат недоступен) — не считать сбоем, тихо пропустить и
убрать из списка.

**Не удалять:** сообщения, не относящиеся к гейту.

## 6. Тестовый план (минимум)

1. Токен работает как `automation_key` в течение объявленного окна.
2. Токен **не** работает после истечения — даже без явного отзыва.
3. Токен **не** работает после явного отзыва, до истечения срока.
4. Сгенерировать/отозвать окно может только владелец (chat_id-проверка).
5. Операции под временным токеном помечены в отчёте отдельно от операций
   под `AUTOMATION_KEY` и от операций под устаревшим `MCP_SECRET`.
6. Активное окно не мешает и не подменяет `AUTOMATION_KEY`/`MCP_SECRET` —
   все каналы работают независимо и одновременно.
7. Просроченная/отозванная запись остаётся в базе (не удаляется) — та же
   дисциплина, что у `mark_consumed` (`manifest_store.py:443`): гасить, не
   стирать, история остаётся.
8. `AUTOMATION_KEY` работает как ключ независимо от `MCP_SECRET`.
9. `MCP_SECRET` по-прежнему работает как ключ (обратная совместимость,
   раздел 2) — до отдельной правки, которая это уберёт.
10. Повторная генерация окна при уже активном — старый токен перестаёт
    работать, новый работает, окно продлено.
11. Сообщение с планом не удаляется, пока не пришёл ответ, даже если прошло
    больше минуты ожидания.
12. Сообщение с планом удаляется примерно через минуту ПОСЛЕ ответа (не от
    момента отправки).
13. Отчёт удаляется примерно через минуту после отправки.
14. Сбой удаления (сообщение уже стёрто/чат недоступен) не роняет поллер и
    не переотправляет ошибку владельцу.

## 7. Явно вне рамок этого ТЗ

- Не входит в перечень 18 пунктов "Заход 1" — отдельная работа/заход.
- Портирование `automation_key.py` в другие MCP-репо (gmail-mcp,
  calendar-mcp, drive-mcp, docs-mcp, sheets-mcp) — не сейчас, только
  ticktick-mcp.
- Удаление `MCP_SECRET` из списка принимаемых automation_key — отдельная
  будущая правка, после того как владелец переведёт внешние автоматизации.
