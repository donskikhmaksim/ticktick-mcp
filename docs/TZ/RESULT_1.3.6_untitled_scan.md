## Как измерено

1. **Полный проход открытых задач вне закрытых проектов.** `get_all_tasks`
   отдаёт дерево «Inbox + все НЕ-архивные проекты» одним источником (v2
   sync state), постранично (soft cap 200 задач/страница, шаг считается по
   top-level). Пройдены ВСЕ страницы без пропусков — 12 вызовов покрывают
   top-level 1–1182 (1405 задач с подзадачами) сплошным диапазоном; последняя
   страница (offset=1170) дошла до 1182 без хвоста. Проверка на разрывы: три
   первых захода шли шагом 200 «наугад» и создали дыры на границах страниц
   (offset 379↔400, 548↔600, 774↔800, 986↔1000, где предыдущая страница
   заканчивалась НЕ на круглой сотне из-за плавающей границы поддерева) —
   дыры закрыты отдельными вызовами на точные offset из футера предыдущего
   ответа.
2. **Закрытые/архивные проекты.** `get_projects` показал 27 проектов, из
   них два помечены `Closed: Yes` — «🧠Assistant»
   (`699d03848f0853b739baf1d6`) и «Personal goals»
   (`69ead2874f0f112a11ab2911`). `get_all_tasks` их НЕ читает (v2 sync pool
   закрытые проекты не включает — тот же факт документирован в самом
   сервере, см. ветку `scope='closed'` у `search_all_tasks`). Оба закрытых
   проекта запрошены отдельно через `get_project_tasks` — «No tasks found»
   в обоих. Задач там нет вообще, безымянных в том числе.
3. **Подзадачи.** Подзадачи в TickTick — обычные задачи с `parentId`;
   `get_all_tasks` печатает их вложенными («↳ …») под родителем, но это тот
   же плоский пул — они читаются на равных, не отдельным проходом.
4. **Опознание «пустого» на этом снимке.** У задачи `6a73adfcbf08801000f174bf`
   строка списка показала буквально `(no title)` — это МАРКЕР СТАРОЙ,
   ещё не задеплоенной на боевой сервер версии кода (в `wt-z136`/`main`
   этого репозитория title-заменитель уже другой — `(без названия: …)`,
   см. `ticktick_mcp/src/server.py::_untitled_label`). Значит боевой
   MCP-сервер, к которому идёт `mcp__ticktick__*` в этой сессии, СТАРШЕ
   локального кода: он ловит `title is None` и `title == ""` (простая
   falsy-проверка), но НЕ обязан ловить пробельные/невидимые названия тем же
   явным маркером. Прямой `get_task` на этот id подтвердил `Title: ` —
   действительно пустая строка, не артефакт форматирования.
5. **Прицельная проверка невидимых/пробельных классов.** Простым
   визуальным просмотром 1400+ строк нельзя надёжно поймать
   zero-width-space/BOM/NBSP-only названия — визуально они неотличимы от
   обычного пробела. Поэтому дополнительно: `search_all_tasks(query=<символ>,
   fields="title", scope="both")` для zero-width space (U+200B), BOM
   (U+FEFF) и таба (U+0009) — по всем трём **0 совпадений** ни в открытых,
   ни в закрытых проектах. Поиск по обычному пробелу вернул 1329 совпадений
   (слишком широкий запрос — почти любое название содержит пробел, годится
   только чтобы подтвердить, что сам механизм поиска по подстроке в title
   работает и не молчит).

## Что НЕ измерено (честно, не выдумано)

- **Названия из ОДНОГО обычного пробела/таба или из одного NBSP без других
  символов** — не подтверждены и не опровергнуты отдельным точным поиском:
  инструмент поиска не умеет искать «title состоит ТОЛЬКО из символа X»,
  только подстроку, а подстрока-пробел даёт слишком широкий (бесполезный)
  результат. Прикрыто только визуальным построчным просмотром всех страниц
  `get_all_tasks` — этот способ НЕ гарантирует, что такой случай был бы
  замечен (пробел визуально неотличим от его отсутствия при беглом чтении
  строки в 100+ символов).
- **Сырые JSON-поля задач** (raw `content`/`desc`/`attachments`) не
  прочитаны напрямую — весь снимок собран через уже отформatированный
  текстовый вывод `mcp__ticktick__*`, который является санкционированным
  read-only каналом этой сессии к живому аккаунту (доступ к самим
  учётным данным/токену в файле `.env` НЕ запрашивался и не
  использовался — команда `grep`/`awk` по `.env` была заблокирована
  классификатором безопасности среды при попытке даже маскированной
  проверки, попытки повторить это через обход не предпринимались).
- **Версия боевого MCP-сервера** позади локального кода `wt-z136`/`main`
  (см. п.4 выше) — прежний, более примитивный, слой определения «пустого
  названия» на боевом сервере не эквивалентен новому `_looks_untitled`.
  Итоговое число «1» получено НЕ через переиспользование живой продовой
  логики (она устарела), а через прямое подтверждение сырого `Title: `
  плюс прицельные точечные поиски по невидимым символам — это ближе к
  «ручной аудит с точечной проверкой», чем к «доверие маркеру списка».
