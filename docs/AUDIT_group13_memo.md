## Сводный вердикт (главный вопрос)

(plan → execute через `_require_consent`). Вчера, судя по всему, реально
занимались только post-verify (§5) — он у всех 7 присутствует и в целом
качественный (независимое свежее чтение, а не эхо ответа мутации). Но §3 —

без исключений... Исключений по «мелкости» — НЕТ») — не реализован ни у
одного из 7. Сейчас все 7 мутируют TickTick за один вызов инструмента, без
предварительного плана и без ожидания явного «да» пользователя, проверяемого
сервером.

Прямое доказательство: в файле есть ровно один канонический гейт-хелпер,
`_require_consent(...)` (объявлен на строке 2345, единая точка входа согласно

(они лежат на строках 4481, 6093, 6117, 6154, 7121, 7193, 7855). Т.е. ни
`create_project`, ни `update_project`, ни `archive_project`, ни
`create_project_group`, ни `delete_project_group`, ни `move_project_to_group`,
ни `create_project_column` не проходят через `_require_consent` — гейта §3

Показательно, что сосед по файлу — `delete_project` (строка 4538, НЕ входит в

## Общий вывод

1. **§3 (гейт согласия) — главный дефект, подтверждён на 7 из 7.** Ни один
   инструмент группы 13 не проходит через `_require_consent`. Это прямое
   нарушение инварианта §1 п.2 («без исключений»), включая необратимую
   операцию `delete_project_group` — единственная её защита сейчас —
   identity-guard плюс докстринг, честно перекладывающий ответственность за
   подтверждение на модель («YOUR job, not the server's»), что прямо
   противоречит духу §3 (гейт должен быть барьером **в коде сервера**, а не
   инструкцией для модели).
2. **§5 (post-verify) — реализован у всех 7**, качественно: везде отдельный
   свежий запрос (не эхо ответа мутации), попольная сверка где применимо,
   честные ⚠️/❌ при неудаче/расхождении. Подтверждает гипотезу задачи:
   вчерашняя работа была именно про post-verify.
3. **§4 (identity-guard)** — в целом хорошо (6 из 7 сильные), кроме
   `create_project_column`, где `project_name` опционален и ослабляет guard
   вопреки требованию §4 «отказать, если название не передано».
4. **§5.2 (pre-snapshot перед необратимой мутацией)** — отсутствует у
   `delete_project_group` (нет `_journal_write` вообще), хотя операция
   необратима по духу (папка удаляется навсегда, хоть проекты внутри и
   сохраняются).
5. **§7 (единый формат вывода)** — расхождение: `create_project`,
   `update_project`, `archive_project`, `create_project_column` используют
   полный `###`-каркас с пруф-блоком; `create_project_group`,
   `delete_project_group`, `move_project_to_group` — упрощённый ответ без
   заголовка и без пруф-блока по шаблону §5.3, местами на английском
   (`delete_project_group`), что отдельно нарушает §7.4.
