# Аудит группы 14: create_subtask, abandon_task, duplicate_task, create_tag, rename_tag, delete_tag

READ-ONLY анализ. Прогон §3 (гейт) / §4 (identity-guard) / §5 (post-verify) / §6
(fail-closed) / §7 (формат) / §16 (чек-лист) СТАНДАРТА против
`ticktick_mcp/src/server.py`. Ничего в коде не менялось.

## Вердикт одной строкой

Все шесть — write-методы БЕЗ серверного гейта plan→execute (§3, инвариант 2).
Единственное исключение — ветка слияния тегов внутри `rename_tag`
(строки 6875-6884), которая гейтится вручную через `_require_consent`. Обычная
(не сливающая) ветка `rename_tag`, а также весь `create_subtask`,
`abandon_task`, `duplicate_task`, `create_tag`, `delete_tag` мутируют сразу по
первому вызову — гейта нет вообще.

## create_subtask — строка 5163

- **§3 Гейт:** ❌ отсутствует. Мутирует сразу, `_require_consent` не вызывается
  ни разу в теле функции.
- **§4 Identity-guard:** ✅ есть, `_guard_task(parent_task_id, parent_task_title, project_id)`
  (5193) — id + название + контейнер (project_id), свежая перечитка через
  `_guard_task`. Соответствует §4 по родителю; для самой создаваемой подзадачи
  guard неприменим (её ещё нет).
- **§5 Post-verify:** ✅ реальный — отдельный `_open_by_id(fresh=True)` (5222),
  сверка по `parentId`, три исхода ✅/⚠️/❌ (5224-5235).
- **§6 Fail-closed:** ✅ частично — guard-миссы отказывают явно с 🛑, но общий
  гейт согласия отсутствует, поэтому «фактическое согласие человека» не
  проверяется вообще (только identity, не consent).
- **§7 Формат:** ⚠️ нет `###`-заголовка (§7.1 каркас), нет общего
  хелпера-обёртки; эмодзи-легенда (✅/⚠️/❌) соблюдена частично.

## abandon_task — строка 6934

- **§3 Гейт:** ❌ отсутствует полностью.
- **§4 Identity-guard:** ✅ `_guard_task(task_id, task_title)` (6951) —
  id + название, свежая перечитка. Контейнер (проект) не передаётся/не
  проверяется — слабее полного трёх-признакового guard §4, но для «Won't do»
  без смены проекта это менее критично.
- **§5 Post-verify:** ✅ реальный, `_open_by_id(fresh=True)` (6964), три исхода.
- **§6 Fail-closed:** аналогично create_subtask — guard есть, гейта согласия
  нет.
- **§7 Формат:** ⚠️ то же — нет ###-заголовка/общего хелпера.

## duplicate_task — строка 6978

- **§3 Гейт:** ❌ отсутствует.
- **§4 Identity-guard:** ✅ `_guard_task(task_id, task_title)` (6994), как у
  abandon_task — id+название, без явной проверки контейнера.
- **§5 Post-verify:** ✅ реальный, `_open_by_id(fresh=True)` (7011), три исхода
  + честная оговорка «в копию не переносятся items/column/parent» (7020-7021).
- **§6 Fail-closed:** гейта согласия нет (только identity).
- **§7 Формат:** ⚠️ нет ###-заголовка.

## create_tag — строка 6814

- **§3 Гейт:** ❌ отсутствует полностью — ни манифеста, ни `_require_consent`.
- **§4 Identity-guard:** ❌ нет вообще — нет проверки, не существует ли уже тег
  с таким именем/цветом; для create это не всегда обязательно по духу §4
  (создание нового объекта, не мутация существующего), но нет даже
  дубликат-проверки (§10.3 «а не сделано ли уже»).
- **§5 Post-verify:** ⚠️ частичный — `_live_tag_names()` (6824) сверяет только
  наличие имени, НЕ сверяет цвет и НЕ даёт исход ❌ (только ✅ или ⚠️, третий
  исход §5.3 фактически недостижим).
- **§6 Fail-closed:** нет отказов вообще — нечего гейтить, поэтому
  fail-closed неприменим (create без риска перезаписи).
- **§7 Формат:** ❌ нет ###-заголовка, эмодзи-легенда неполная (нет ❌-ветки).

## rename_tag — строка 6843

- **§3 Гейт:** ⚠️ **частично**. Ветка слияния (когда `new_name` уже существует)
  ГЕЙТИТСЯ: `_require_consent(action="rename_tag_merge", tier=2, manifest=None,
  user_reply=user_reply)` (6875) + требует `allow_merge=True`. НО обычное
  переименование (new_name свободен) — **без гейта вообще**, мутирует сразу
  (6885). По инварианту 2 «Гейт у ВСЕХ write, без исключений» это дефект: не
  только слияние необратимо теряет данные — сама операция переименования
  тоже мутация, требующая plan→execute.
  Также сам вызов `_require_consent` с `manifest=None` — не полный
  plan→execute паттерн §3.1 (нет фазы 1 «построй манифест, покажи превью,
  дождись ответа»): это одноразовая проверка `user_reply` внутри execute-фазы,
  без сохранённого манифеста и без `object_hash`-привязки (§3.3 п.2 не
  выполним при `manifest=None`).
- **§4 Identity-guard:** ⚠️ частичный — проверка существования `old_name`
  (6867-6872) с подсказкой похожих имён, но не полноценный id+название+
  контейнер (у тегов нет контейнера в этом смысле, приемлемо).
- **§5 Post-verify:** ✅ реальный, `_live_tag_names()` после мутации (6887),
  три исхода (❌/❌/успех), НО итоговая успешная строка (6895) — **БЕЗ эмодзи**
  (нет ✅) и **на английском** («Tag 'X' renamed to 'Y' (проверено)» —
  смешение языков нарушает §7.4).
- **§6 Fail-closed:** ✅ для слияния (отказ 🛑 без allow_merge/user_reply),
  ❌ для обычного пути (нет отказа/гейта).
- **§7 Формат:** ❌ явное нарушение §7.4 (английский в пользовательском
  тексте без причины) и §7.2 (успех без эмодзи из легенды).

## delete_tag — строка 6902

- **§3 Гейт:** ❌ отсутствует полностью. Удаление тега — необратимая (сняли со
  всех задач) операция, по §1 инварианту 2 гейт обязателен без исключений «по
  мелкости/обратимости» — здесь исключения делать нельзя, а гейта нет.
- **§4 Identity-guard:** ⚠️ только существование (6908-6913), похожие имена
  подсказаны (латиница/кириллица) — разумно, но не id+контейнер (у тегов
  этого нет).
- **§5 Post-verify:** ✅ реальный, `_live_tag_names()` (6917), явный подсчёт
  «снято с N задач» (6920-6921) — хорошая практика радиуса поражения, но
  **pre-snapshot (§5.2) отсутствует**: `carriers` считается ДО удаления
  (6915) правильно по духу, но сам список задач-носителей нигде не
  записывается в аудит-лог (только счётчик в тексте ответа) — ручной откат
  «какие задачи носили тег» невозможен, что прямо противоречит §5.2.
- **§6 Fail-closed:** ✅ отказ 🛑 при несуществующем теге, но нет отказа
  «требуется согласие» — гейта согласия нет вообби.
- **§7 Формат:** ⚠️ нет ###-заголовка/общего хелпера, но эмодзи-легенда (🛑/✅/❌)
  соблюдена лучше остальных пяти.

## Сквозные наблюдения (§16 чек-лист, пункты 1-2 особенно)

- **П.2 «ровно один `require_consent`, все write через него»** — НЕ
  выполняется для всей группы 14: 5 из 6 методов вообще не вызывают
  `_require_consent`; 1 (`rename_tag`) вызывает его только в одной ветке.
  Рефлексивный тест §13 «нет write-метода, минующего require_consent» на
  этих шести упадёт.
- **П.1 аннотации:** все шесть объявлены как `@mcp.tool()` без параметра
  `annotations` — нет общей WRITE-константы (в файле есть только `READONLY`,
  строка 52); явного `readOnlyHint=False`/`destructiveHint` нет ни у одного —
  нарушение §2.1.
- **П.5 манифест:** ни у одного из шести нет манифеста/TTL/`object_hash` —
  ожидаемо, раз гейта нет.
- **П.8 формат:** ни один не использует общий хелпер-обёртку §7.1 (нет
  `###`-заголовка ни у одного из шести); `rename_tag` вдобавок ломает язык
  (§7.4).
- **П.13 аудит-лог:** `create_subtask`, `abandon_task`, `duplicate_task`
  пишут в журнал через `_op_journal(...)` — так что post-mutation запись
  есть. `create_tag`, `rename_tag`, `delete_tag` — журнала НЕ ведут вообще
  (в `create_tag` это даже явно закомментировано: «tag creation isn't
  journaled», 6822-6823) — нарушение §11 «каждая мутация ДОЛЖНА писать одну
  строку в аудит-лог».
