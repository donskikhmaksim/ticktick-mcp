Дата: 2026-07-29. Файл: `ticktick_mcp/src/server.py`. Прогнан чек-лист §16 по §3
(гейт plan→execute), §4 (identity-guard), §5 (post-verify, ОСОБО pre-snapshot
§5.2), §6 (fail-closed), §7 (единый формат вывода) для: `delete_tasks`
(2090-2217), `plan_task_deletion` (2536-2659), `execute_task_deletion`
(2662-2696) + общий движок `_execute_task_deletion_impl` (2699-2810),
`delete_task_with_subtasks` (4443-4478), `delete_project` (4538-4668).

- §4 identity-guard: ✅ title обязателен на входе (2157-2160), id+title+project

### 2. `plan_task_deletion` + `execute_task_deletion` (server.py:2536-2696)
- §3.1 форма API: ❌ **АРХИТЕКТУРНОЕ РАСХОЖДЕНИЕ, зафиксировано явно.** Это ДВЕ
  отдельные зарегистрированные `@mcp.tool()`-функции (`plan_task_deletion` —
  READONLY, `execute_task_deletion` — write), а не одна функция с двумя режимами
  вызова, как требует §3.1: «Гейт ДОЛЖЕН быть реализован как один инструмент с
  двумя режимами вызова, а не как пара `plan_x`/`execute_x`». Причина в
  стандарте прямая цитата: «три разных паттерна гейта в одном сервере (как
  получилось в ticktick-mcp) — это гарантированный разнобой и дыры» — это
  буквально констатация текущего состояния этого сервера, а `plan_x`/`execute_x`
  — один из тех паттернов.
- Смягчающее обстоятельство (не отменяет дефект, но снижает его опасность):
  обе функции **не мутируют в обход общей точки входа** — `execute_task_deletion`
  идёт через `_require_consent(tier=2, ...)` (2691-2695) и тот же
  `_execute_task_deletion_impl`, что и `delete_tasks`. То есть единый
  `require_consent`-хелпер (§3.1, требование «внутренний помощник
  `require_consent(...)`, через который проходят ВСЕ write-вызовы») соблюдён;
  нарушена именно **форма публичного API** (два инструмента вместо одного), не
  сам гейт по существу.
- Причина существования пары именно так, как написано в комментарии кода
  (2220-2228): рассчитана на «agent/autonomous flows», где `plan_*`
  предсказуемо READONLY-аннотирован для клиентского авто-разрешения read-вызовов
  — это осознанный трейд-офф автора, но стандарт (написанный уже ПОСЛЕ этого
  кода, 2026-07-28) явно запрещает такую форму без исключений «по мелкости».
  **Чинить: слить в `delete_tasks`-подобную сигнатуру одной функции, либо явно
  зарегистрировать как единственное системное исключение с обоснованием в
  `docs/` — на усмотрение Максима, я не переписываю код.**
- §4 identity-guard: ✅ в `_execute_task_deletion_impl` (2699-2810) — id, title
  (`_names_agree`, 2741), project (по id и по имени, 2748-2760) — все три
  признака, для каждого элемента манифеста (в т.ч. развёрнутого поддерева).
- §5.1 post-verify: ✅ реальный — отдельный свежий `_open_by_id(fresh=True)`
  ПОСЛЕ `batch_delete_tasks` (2774), не переиспользование ответа мутации;
  `still is None` → явное ⚠️, не тихий успех (2776-2779).
- §5.2 pre-snapshot: ✅ **реально пишется В АУДИТ-ЛОГ ДО удаления** — проверено
  построчно: `journal = _journal_write(...)` на строке 2764-2768 выполняется
  ДО вызова `ticktick_v2.batch_delete_tasks(...)` на строке 2771-2772. Снапшот
  включает поля `content/desc/dueDate/startDate/priority/tags/projectId/
  parentId/columnId/isAllDay` (`_snapshot_of`, 2422-2427) — этого достаточно
  для ручного восстановления, как и требует §5.2. Путь снапшота
  выводится пользователю в ответе (2799-2802: «Снапшоты удалённого — в
  журнале: … восстановление: restore_tasks из корзины, либо пересоздание из
  снапшота»).
- §5.3 формат пруфа: ✅ `_build_operation_report` приклеивается сервером
  (2805-2806), не предлагается вызвать отдельно.
- §7 формат вывода: ⚠️ **частичное расхождение.** Итоговый ответ
  `_execute_task_deletion_impl` (2775-2807) НЕ начинается с `### <эмодзи>
  <заголовок>` — это плоский список строк без каркаса §7.1 (например
  «🗑 Удалено N/M: …»). Эмодзи **🗑** не входит в замороженную легенду §7.2
  (✅/⚠️/❌/🛑/↷/🧾) и используется как статусный маркер успеха вместо ✅ — это
  прямое нарушение «новые значки — только через правку файла §7.2». То же самое
  в `delete_project` (см. п.5 ниже, строка 4662). Функционально результат
  читаем и честный (успех/провал видны), но формально не проходит §7.1/§7.2.
- **Вердикт: `plan_task_deletion` — ✅ по существу (read, честный докстринг,
  капы max_items есть); `execute_task_deletion` — ⚠️ по существу гейта/пруфа
  корректен, но пара как целое — ❌ по форме §3.1 (архитектурное расхождение);
  плюс отдельный ⚠️ по §7 (заголовок/эмодзи-легенда).**

### 3. `delete_task_with_subtasks` (server.py:4443-4478)

  обещать функциональность, которой нет.
- §6 fail-closed: ✅ тривиально соблюдён (единственный путь — отказ).
- **Вердикт: ✅ соответствует** (корректно спроектированная заглушка, не

### 4. `delete_project` (server.py:4538-4668)
- §3.1 форма API: ✅ одна функция, два режима по `user_reply` (без манифеста —
  инлайн-гейт, что стандарт прямо допускает для 🔴-случаев без `plan_shown_at`,
  §3.5 комментарий в коде `_require_consent`: «used here only for the
  one-shot/TTL/binding/timing checks… When None, this is an inline (non-manifest)
  🔴 check»). Количество задач и сэмпл читаются СВЕЖИМИ на КАЖДОМ вызове
  (4571-4586), а не кэшируются между 1-м и 2-м вызовом — исключает удаление по
  протухшему счётчику.
- §3.3 гейт: ✅ через общий `_require_consent(tier=2, ...)` (4588-4589).
- §4 identity-guard: ✅ `_guard_project(..., fresh=True, require_known=True)`
  (4566-4567) — отказ, если id не резолвится.
- §5.2 pre-snapshot: ✅ **реально пишется ДО удаления** — `_journal_write` для
  самого проекта (4619-4624) И для ВСЕХ содержащихся задач (4625-4634)
  выполняются ДО `ticktick.delete_project(project_id)` на строке 4637. Это
  особенно важно здесь: удаление проекта каскадно уносит все задачи, и без
  этого снапшота восстановить их было бы физически нечем — стандарт (§5.2)
  прямо указывает этот случай как обоснование pre-snapshot.
- §5.1 post-verify: ✅ отдельный свежий `_v2_project_names_or_none()` ПОСЛЕ
  `invalidate_cache()` (4643-4648); `None` (сбой чтения) → явное ⚠️, не
  «удаление подтверждено по умолчанию» (4650-4657) — корректный fail-closed на
  проверке.
- §7 формат: ⚠️ то же расхождение, что у execute_task_deletion — ответ не
  начинается с `### <эмодзи>`, использует незалегендированный **🗑** вместо ✅
  для успеха (4662-4663).
- **Вердикт: ✅ по существу гейта/pre-snapshot/post-verify; ⚠️ то же §7
  расхождение по формату вывода, что и у execute_task_deletion.**

**Главный дефект группы:** `plan_task_deletion`/`execute_task_deletion` —
архитектурное расхождение с §3.1 (два инструмента вместо одного) — это ИМЕННО
тот паттерн, который §3.1 стандарта цитирует как источник разнобоя в этом же
репозитории. По существу защиты (гейт/identity/pre-snapshot/post-verify) обе
функции корректны — расхождение чисто в форме публичного API, не в дыре
безопасности.

**Второй дефект (мельче, встречается в обоих write-путях удаления):**
использование эмодзи **🗑** вне замороженной легенды §7.2 и отсутствие
`###`-заголовка первой строкой в `_execute_task_deletion_impl` и
`delete_project` — расхождение с §7.1/§7.2, не влияет на безопасность, влияет
на единообразие вывода.

Код не менялся — это read-only ревизия по прямому запросу Максима.
